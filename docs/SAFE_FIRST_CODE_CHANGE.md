# 第一次安全修改论文代码

用于已经跑通最小 baseline、准备修复问题或尝试第一个方法改动的读者。目标不是把科研代码变成大型软件工程，而是确保一次改动能够解释、验证和回退。

> 先确认改动属于什么，再决定怎么验证。测试通过只能说明已检查的行为没有失败，不能自动证明方法正确、比较公平或研究假设成立。

## 1. 什么时候使用

出现以下任一情况时，先完成本指南：

- 为适配路径、设备、依赖或数据目录而修改代码；
- 修复 baseline 中疑似实现错误；
- 重构 Notebook、训练循环或配置结构；
- 增加日志、指标、断点或可视化；
- 修改模型、损失、数据处理、优化器或评价流程；
- 接受 AI 生成或大幅补全的代码。

如果未修改的官方最小命令仍不能运行，先继续[复现排障](../templates/10-debug-help-request.md)，不要把环境修复与研究方法改动混在一起。如果 baseline 尚未取得 `READY_FOR_CHANGE`，先完成[稳定化门](BASELINE_STABILIZATION_GATE.md)。

## 2. 先给改动分类

一次提交只保留一种主要类别。无法归类通常意味着范围过大。

| 类别 | 例子 | 能否直接证明方法有效 |
| --- | --- | --- |
| `ENVIRONMENT_REPAIR` | 路径、设备、依赖兼容、下载入口 | 不能 |
| `BASELINE_REPAIR` | 修复与论文或官方实现不一致的明确错误 | 不能；需要重新锁定 baseline |
| `REFACTOR` | 拆函数、改目录、整理配置，但声明行为不变 | 不能 |
| `INSTRUMENTATION` | 增加日志、断言、指标或 checkpoint | 不能；还要确认没有改变执行行为 |
| `RESEARCH_CHANGE` | 模型、损失、数据、训练或推理方法改动 | 只能产生待验证的候选方法 |

不要在同一个 diff 中同时完成重构、修 bug 和方法创新。确实都需要时，按“修复并验证 → 重构并验证 → 方法改动并验证”的顺序建立独立提交。

## 3. 修改前冻结基线

在编辑文件或让 AI 写代码前记录：

```text
上游仓库与 base commit：
当前分支与工作区状态：
baseline run_id、命令、配置、环境和日志：
当前可观察行为与已知差异：
本次唯一目标：
允许修改的文件：
禁止修改的文件或目录：
计划运行的检查：
回退点：
```

最低要求：

- 工作区的既有改动已识别，不覆盖导师或合作者尚未提交的内容；
- baseline 的命令、配置、数据版本、指标和日志可以相互定位；
- 新建用途明确的分支，或在个人仓库中至少记录 base commit；
- 数据划分、评测脚本和测试集默认列为禁止修改；若研究问题必须修改，单独声明并重新冻结协议；
- 密钥、受限数据、权重、大文件和匿名材料不会进入提交。

## 4. 先写最小修改计划

计划应能用四句话回答：

1. 哪个现象或错误触发这次修改？
2. 准备改哪个文件、函数或配置项？
3. 哪些行为必须保持不变？
4. 什么结果会接受、拆分、复核或放弃这次修改？

让 AI 协助时，先要求它只读理解仓库并返回“目标—文件—风险—检查”计划。确认计划后再生成最小 patch；不要直接批准批量格式化、目录迁移、依赖升级或多模块重写。

## 5. 按主张选择检查

不是每次都必须跑完整训练，但检查强度必须覆盖这次改动声称影响的行为。

| 层级 | 适用改动 | 最低证据 |
| --- | --- | --- |
| **T0 入口** | 文档、配置、依赖或轻量改动 | import、`--help`、配置解析、静态检查或项目已有快速检查 |
| **T1 局部行为** | 函数、shape、数值或数据转换 | 项目已有单元测试；或固定输入的 shape、dtype、范围和数值断言 |
| **T2 最小训练** | 模型、loss、梯度或训练循环 | 一个 batch / 极小数据运行；loss、梯度、参数更新与 NaN / Inf 检查 |
| **T3 配对 pilot** | 候选方法 | 同一数据、配置、预算和评测下的 baseline / 候选成对运行 |
| **T4 代表性确认** | 准备形成研究结论 | 冻结协议下的代表性规模、计划重复、完整失败与成本记录 |

路径修复通常需要 T0–T1；训练逻辑修改至少需要 T0–T2；方法收益主张需要 T3，主要结论还需要 T4。优先运行项目已有测试和官方最小命令；新增检查应针对真实风险，不为追求数量制造无关测试。

## 6. 逐项审查 diff

不要只看“代码能运行”。逐文件检查 `git diff`，尤其关注：

- **数据**：来源、split、过滤、去重、顺序、预处理、增强和缓存键；
- **方法**：模型结构、loss、初始化、优化器、学习率、scheduler 和默认参数；
- **评价**：指标实现、阈值、聚合、统计单位、测试集访问和最好 checkpoint 选择；
- **随机性**：seed 设置、采样器、数据顺序和确定性选项；
- **状态**：checkpoint 保存 / 恢复、训练与评测模式、梯度开关；
- **输出**：日志字段、路径、覆盖旧结果和失败时是否仍写入“成功”产物；
- **依赖**：新增包是否真实存在、版本和 API 是否匹配、许可证与来源是否可接受；
- **测试**：是否删除、跳过、放宽断言，或只修改测试来迁就新实现；
- **兜底**：是否静默吞掉异常、换数据、换指标、换模型或返回看似合理的默认结果。

格式化和生成文件造成的大 diff 应先排除或单独提交。研究改动中出现无关依赖升级、评价脚本变化或测试删除时，默认选择 `SPLIT_CHANGE`。

## 7. AI 生成代码的接受条件

AI 生成的代码只有同时满足以下条件才进入 pilot：

- 研究者能用自己的话解释改了什么、为什么与预期数据流；
- 实际 diff 与批准的文件范围一致，没有隐藏改动；
- 新增 API、依赖、命令和配置项已从项目源码或官方文档核验；
- 修改前后的最小检查均有命令、退出状态和日志；
- 数据、baseline、评价协议和测试没有被偷偷改变；
- 未删除失败运行、未只保存最好结果，也未把模拟输出当真实实验；
- 提交能够独立回退，并关联对应的 `run_id`。

第二位审阅者很有价值，但个人项目不强制创建 PR。没有同伴时，至少隔一段时间重新阅读 diff，并根据冻结计划逐项自审。

## 8. 提交与回退

推荐提交顺序：

```text
base commit
  → environment / baseline repair
  → behavior-preserving refactor or instrumentation
  → one research change
  → experiment record linked by run_id
```

提交信息说明改动目的，不写笼统的“update”。保留失败尝试及其原因，但不要提交大体积运行产物。需要撤销已提交改动时，优先使用新提交恢复或 `git revert`；未确认目标前不要使用会覆盖工作区的破坏性命令。

## 9. 只作一个准入决定

| 状态 | 含义与下一步 |
| --- | --- |
| `SAFE_FOR_PILOT` | 范围、diff 和最低检查均通过，可以开始受控 pilot。 |
| `SPLIT_CHANGE` | 混入多个类别或无关文件；拆成独立修改后重审。 |
| `REPAIR_BASELINE_FIRST` | 发现 baseline 或评测问题；修复并重新稳定化，不比较方法。 |
| `REVIEW_REQUIRED` | 依赖、数据、评价、安全、许可证或实现仍不能独立判断；请求复核。 |
| `REVERT_AND_REPRODUCE` | 修改无法解释、检查失败或证据链断裂；回退并从已知 baseline 重来。 |

## 10. 验收清单

- [ ] 改动类别、唯一目标、base commit 和分支已记录；
- [ ] 修改前 baseline 证据可以定位；
- [ ] 允许与禁止修改范围明确；
- [ ] 修复、重构、观测和方法改动没有混在一个提交；
- [ ] 检查覆盖本次主张，且修改前后证据均已保存；
- [ ] 已逐文件审查数据、方法、评价、随机性、状态、输出、依赖和测试；
- [ ] 能解释 AI 生成的每个研究相关改动；
- [ ] 未静默更换数据、指标、默认参数或失败状态；
- [ ] commit、配置、run_id、日志和结果能够互相定位；
- [ ] 已选择一个准入状态并写明下一步。

## 依据与延伸阅读

- [Learning Research](https://github.com/pengsida/learning_research)：将实验能力建立在写代码、分析失败和持续实验记录上；其 3D Vision 课程与实验室培养路径不是通用前置；
- [AutoResearchClaw](https://github.com/aiming-lab/AutoResearchClaw)：参考其阶段产物、人工检查点、预算、版本化和继续 / 优化 / 转向决策；本指南不采用“一键自动研究”作为结果可信性的替代；
- [Google Engineering Practices：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)：小而自包含的改动更容易审查、测试和回退，并建议把重构与功能修改分开；
- [GitHub：Helping others review your changes](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes)：用聚焦改动、上下文、自审 diff 和测试帮助审阅；
- [GitHub Copilot：Review AI-generated code](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code)：检查意图、测试、依赖、虚构 API、删除或跳过测试等 AI 代码风险；
- [Releasing Research Code](https://github.com/paperswithcode/releasing-research-code)：依赖、训练、评价、权重与精确命令共同构成可复查代码入口。
