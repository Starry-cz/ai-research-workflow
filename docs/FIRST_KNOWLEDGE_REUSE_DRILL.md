# 第一次检索并安全复用研究知识

这份教程面向第一次接手 AI / 计算机科研项目的读者。目标不是背住一条“正确答案”，而是亲手完成一次：从自己看到的模糊症状出发，找到候选知识，排除相似但不适用的条目，核对当前证据，再作出一个可审计决定。

```text
原始症状 → 查询阶梯 → 候选集合 → 身份与状态核对
        → 最小验证 → 复用决定 → 结果写回
```

> 找到一条看起来相似的经验，不等于已经找到当前问题的根因。检索负责召回候选，诊断负责排除错误候选；两者不能合并成“搜索结果第一条就是答案”。

## 1. 为什么还需要单独演练

[研究知识提炼指南](RESEARCH_KNOWLEDGE_CAPTURE.md)已经说明如何写标题、标签、适用范围和状态，但它主要是一份执行参考。零基础读者还需要在安全的教学项目中练习以下动作：

- 不用自己猜测的原因作第一条查询；
- 从终端原文提取可复制的错误签名；
- 查看多个候选，而不是只打开排名第一项；
- 区分“症状相似”和“身份、阶段、范围都匹配”；
- 识别 `PROVISIONAL`、`SUPERSEDED`、`RETIRED` 和无来源建议；
- 在运行任何修复前核对代码、文档、数据、权限和副作用；
- 把没搜到、误搜和拒绝复用的原因写回，而不只记录成功答案。

Diátaxis 将教程定义为通过具体行动获得学习经验，而 how-to guide 面向已经知道目标、能够正确采用指导的使用者。因此，一张索引或一份 how-to 不能替代首次练习。

## 2. 先冻结原始问题

在搜索前只记录已经观察到的内容：

```markdown
- 当前任务：
- 预期：
- 实际：
- 第一个关键报错原文：
- 完整命令：
- 当前 commit、配置、数据、环境：
- 已经尝试过什么：
- 当前允许的动作：只读 / 运行 / 修改 / 删除 / 对外求助
```

不要先写“应该是 CUDA”“可能是数据路径”“师兄说删目录就行”。这些可以成为候选假设，但不能伪装成观察。

## 3. 使用查询阶梯

每轮查询只增加一类新信息，并保留查询原文和命中的候选。推荐顺序：

### Q0：使用自己的症状语言

先搜索你会自然描述的现象，例如：

```text
输出目录非空
结果目录拒绝覆盖
训练还没开始就退出
```

即使措辞不够技术准确也应保留。未来读者很可能使用相同语言，没命中的查询也是改进标题和标签的证据。

### Q1：搜索精确错误签名

从文本日志或 traceback 复制最短且有区分度的片段，例如异常类型、错误码或一小段原文。不要只上传截图，也不要复制包含个人路径、token 或受限数据的整段日志到公共搜索。

### Q2：增加阶段和组件

加入发生阶段、函数、模块或数据处理环节，例如：

```text
FileExistsError prepare_output
拒绝覆盖 training output-dir
```

### Q3：增加身份与范围

只有候选仍然过多时，再加入仓库、release / commit、框架、平台、数据或模型身份。先核对本地身份，不要把猜测的版本写进查询。

### Q4：回到原始来源

打开候选条目链接的代码、文档、运行、Issue、配置或决定记录。知识标题和搜索摘要只负责导航，不能替代原始来源。

在本地 Git 仓库中可以优先使用：

```bash
git grep -n -E "输出目录|拒绝覆盖"
git grep -n "FileExistsError"
git grep -n -E "prepare_output|overwrite|output-dir" -- examples/first-workflow-drill
```

GitHub Code Search 还支持引号精确匹配、`repo:`、`path:`、`language:`、布尔表达式和正则表达式。搜索语法只改善召回与缩小范围，不判断科学适用性。

## 4. 候选不是答案

至少记录前两个看似相关候选，逐项核对：

1. **状态**：是否为 `ACTIVE_LOCAL` / `CONFIRMED_REUSE`？是否已经 `SUPERSEDED` / `RETIRED`？
2. **症状**：错误类型、文字、发生阶段和可复现步骤是否一致？
3. **身份**：代码、数据、配置、模型、平台和权限是否在条目范围内？
4. **来源**：条目能否回到当前可访问的原始证据？
5. **安全**：建议动作是否会覆盖、删除、上传、付费、修改共享资产或越权？
6. **区分证据**：哪一项事实能排除其他相似候选？

如果两个候选仍无法区分，正确决定是继续收集一个能区分它们的观察，而不是挑更熟悉或更省事的答案。

## 5. 只做最小验证

验证的目标是区分候选，不是顺便“把问题修好”。优先使用只读和低副作用动作：

- 查看 `--help`、README、当前函数和 `git diff`；
- 检查目录是否为空、文件是否存在、配置是否实际加载；
- 用新临时目录、合成数据或最小样例复现；
- 一次只改变一个变量，并保留修改前后证据；
- 需要删除、覆盖、迁移、公开或访问受限资产时停止并确认授权。

没有稳定复现、来源不可访问、身份不匹配或动作风险不明确时，不得仅凭旧条目执行修复。

## 6. 作出一个复用决定

沿用知识提炼指南的五种决定：

- `APPLY_WITHIN_SCOPE`：身份、症状、来源与权限匹配，执行最小动作；
- `VERIFY_BEFORE_APPLY`：候选相关，但仍有版本、平台或范围差异；
- `DO_NOT_APPLY`：相似候选与当前阶段、原因或权限不匹配；
- `SUPERSEDE_ENTRY`：新证据改变了旧条目的结论、范围或动作；
- `ESCALATE_RESTRICTED`：需要未授权资产、敏感信息或高风险操作。

不得把“没有找到条目”写成“没有已知原因”，也不得把“条目不适用”写成“条目错误”。

## 7. 搜索与复用记录

第一次演练至少留下：

```markdown
- 原始症状与身份：
- Q0 / Q1 / Q2 查询及命中：
- 打开的候选：
- 每个候选的保留 / 排除理由：
- 打开的原始来源：
- 最小区分验证与结果：
- 复用决定：
- 实际动作、副作用与结果：
- 对知识条目的影响：保持 / 补充检索词 / 收缩范围 / supersede / retire
- 仍未解决时的升级问题：
```

Consortium for Service Innovation 的 KCS 指南强调保留请求者最初使用的词语、把事件与知识条目关联，并在复用时审查和改进条目。本仓库只迁移这套检索与反馈闭环，不把技术支持知识库规则当作科研证据或实验结论标准。

## 8. 教学演练与验收

打开[第一次工作流演练](../examples/first-workflow-drill/README.md)，先完成[知识检索练习](../examples/first-workflow-drill/knowledge-retrieval-drill.md)，再核对[已填写结果](../examples/first-workflow-drill/knowledge-retrieval-result.md)。演练包含明确标记的教学干扰项，用来练习排除过期或近似建议；它们不属于正式知识索引，也不得作为项目事实引用。

演练完成至少满足：

- 使用原始症状和精确错误分别搜索过；
- 打开并比较至少两个候选；
- 没有因为标题相似直接执行删除、覆盖或不存在的参数；
- 检查了当前代码 / 文档和至少一个可运行证据；
- 写出唯一复用决定和不超过证据范围的理由；
- 将查询失败、候选排除和运行结果写回。

自动脚本只能验证教学材料、命令和预期证据仍然一致，不能证明陌生新手真正理解。要评价教学可用性，应让未参与编写的人在不提示正确文件的情况下完成任务，记录成功、误用、求助点和卡住位置，再按实际观察修改教程。

## 9. AI 辅助边界

AI 可以帮助生成同义查询、汇总候选差异、指出缺失身份和起草写回记录，但必须遵守：

- 先展示候选与证据，再提出动作；
- 不把搜索排名、相似度或多数回答当作根因证明；
- 不补写未观察到的错误、运行和版本；
- 不自动执行删除、覆盖、上传、付费或共享修改；
- 遇到冲突条目时保留冲突并请求区分证据；
- 不因一条成功复用把状态自动升级为跨项目通用规则。

GitHub 的 Debugging tutor 示例建议从稳定复现、错误信息、最近变化和最小样例开始，并用引导问题建立独立排错能力；`obra/superpowers` 的 systematic-debugging skill 也强调先调查根因、比较差异、单一假设与最小测试。本仓库吸收顺序和证据意识，不把 Copilot 指令或某个 agent skill 当作科研方法学认证。

## 10. 经验、项目与规范依据

- [逻辑排错能力如何执行呢？](https://www.xiaohongshu.com/explore/6a5de291000000000c015350)描述新手在实验失败后重复运行、同时更换很多因素，仍无法定位原因的困境；本教程吸收“分步骤、对照和单变量区分”，不据个人观察规定统一排错成本；
- [最近带了几个研一新生，谈谈感受](https://www.xiaohongshu.com/explore/674a942c0000000007035d9d)强调先明确任务、针对性搜索、按问题类型选择求助对象，并用具体环境与现象降低求助成本；其中学历比较与个人管理经验不作为能力评价规则；
- [我把 AI 翻车记录做成了一张清单](https://www.xiaohongshu.com/explore/6a7546dd0000000033011d5f)用原文、条件、研究对象和作者表述检查 AI 输出；其医学科研语境只用于确认“流畅答案仍需回源”的痛点；
- [知乎：如何正确地在 GitHub 上提 Issue](https://www.zhihu.com/question/21235917/answer/203370582)建议说明环境、复现、预期和实际；该回答年代较早且属个人经验，当前项目模板和上游规则优先；
- [知乎：初学者如何使用 GitHub](https://www.zhihu.com/en/answer/961953665)建议用精确关键词搜索已有 Issue；个人回答只说明检索习惯，不证明第一条结果适用；
- [GitHub Code Search syntax](https://docs.github.com/en/search-github/github-code-search/understanding-github-code-search-syntax)定义精确短语、布尔表达式、`repo:`、`path:` 和正则等查询能力；
- [GitHub Debugging tutor](https://docs.github.com/en/copilot/tutorials/customization-library/custom-instructions/debugging-tutor)强调稳定复现、仔细阅读错误、逐项检查和一次改变一个变量，同时明确示例需要适配具体项目；
- [systematic-debugging](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md)提供从根因调查、模式比较、单一假设到验证的 agent 工作流；它是软件开发 skill，不替代 ML 实验设计、统计推断或领域协议；
- [KCS：Searching is Creating](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/030/010/030)要求记录请求者搜索词、环境与区分特征；[Reuse is Review](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/030/040/020)要求在真实复用中及时改进有价值的条目；本教程只迁移需求驱动维护；
- [Diátaxis Tutorials](https://diataxis.fr/tutorials/)区分“通过行动学习”的教程与面向已具备能力者的 how-to，并要求具体步骤、可见结果和实际用户观察。

## 11. 完成标准

一次安全复用完成时，应能回答：

- 我最初使用了什么词搜索，而不是事后改写成正确术语？
- 哪些候选被打开，为什么保留或排除？
- 当前身份、状态、来源和权限如何核对？
- 哪个最小验证真正区分了候选？
- 采取了哪个决定，动作有什么副作用？
- 这次使用让原条目保持、变得更易检索、收缩范围，还是需要替代？

如果这些问题无法回答，说明完成的是“找到一段文字”，不是可审计的知识复用。
