# 零基础评价协议指南

评价协议先回答“什么证据足以支持当前决策”，再回答“用哪个指标”。如果先看结果再选择指标、阈值、seed 或子集，测试集就参与了方案设计。

```text
主张与决策
  → 错误代价和评价对象
  → 主指标与实现
  → 聚合、阈值和异常处理
  → 统计单位与不确定性
  → 决策门槛
  → 冻结协议后运行
```

## 先写清要做什么决定

每轮实验只回答一个主要问题：

- 是验证代码是否正确，还是比较两种方法？
- 更怕漏掉正例、误报、排序错误、生成不忠实，还是成本过高？
- 模型要泛化到新样本、新用户、新机构、新时间，还是新任务？
- 结果将触发 `PROCEED`、`REFINE`、`PIVOT` 或 `STOP` 中哪种决策？

如果还不能写出失败代价与决策，就没有足够依据选择主指标。

## 一个指标名称不够

对主指标至少记录：

```text
名称与方向：越高越好、越低越好或目标区间
数学定义或可靠文档
代码包、版本、函数与参数
输入格式、正类或标签顺序
macro / micro / weighted / per-group 等聚合
阈值、K、候选集合、匹配或容差规则
无预测、空集合、NaN 和失败样本如何处理
从保存预测重新计算的命令
```

同名指标可能因实现和参数不同而不可比较。不要手抄排行榜数字后只写“按照官方指标”，应锁定官方评测代码、commit、数据版本与命令。

## 区分四类数字

| 数字 | 作用与边界 |
| --- | --- |
| **训练 loss** | 驱动参数更新和诊断优化；下降不等于任务目标必然改善。 |
| **选择指标** | 在验证集上选择超参数、阈值或 checkpoint；不能由测试集代替。 |
| **主测试指标** | 直接对应主要主张；协议冻结后才在测试集计算。 |
| **辅助与诊断指标** | 解释错误、子群体、效率、校准和失败模式；不能在看结果后冒充主指标。 |

如果选择指标与主测试指标不同，要提前解释为什么，以及选择是否可能偏向某类方法。

## 根据错误代价选择指标

### 分类

- 类别大致平衡且错误代价接近时，accuracy 可以作为粗粒度指标，但仍应查看混淆矩阵；
- 正例稀少或漏报代价高时，重点考虑 recall、PR 曲线或任务指定指标；
- 误报代价高时，重点考虑 precision 或 false-positive 相关指标；
- 多分类 / 多标签必须说明正类、标签集合和 macro / micro / weighted / samples 聚合；
- 依赖阈值的指标必须说明阈值在哪个集合上如何选择，`0.5` 不是天然正确。

### 回归、排序、检索与生成

- 回归指标应与误差代价和单位一致，并检查异常值是否支配平均值；
- 排序与检索要写清查询单位、候选集合、相关性标签、`K`、无相关项和重复候选处理；
- 文本、图像或多模态生成的自动指标通常只覆盖部分质量维度，应结合错误分析和必要的人工评价；
- 指标实现、分词、规范化、匹配规则或外部模型发生变化时，旧结果不一定可直接比较。

这些是选择问题的入口，不是跨领域通用答案。目标论文、官方 benchmark 和当前 venue 的协议优先，但仍要审查其是否支持你的新主张。

## 聚合前先确定统计单位

评价表中的一行不一定是独立证据。统计单位可能是：

- 样本、患者、用户、文档、查询、场景、数据集或任务；
- 独立训练 seed、数据重采样、交叉验证 fold 或实验室；
- 人工评价者、被评价项目或两者的组合。

同一患者的多张图、同一文档的多个句子或同一用户的多次交互通常相关。先按正确单位计算或聚合，再形成总体数字；同时报告关键 group 和失败分布，避免大 group 淹没小 group。

比较方法时尽量在同一评价单位上形成配对结果，并保存逐样本或逐 group 预测。采用何种检验、bootstrap 或区间应由数据结构和主张决定，不能只因为软件默认可用就套用。

## 正确描述不确定性

先写明希望描述哪种变化：

- 参数初始化与训练随机性；
- 评价样本抽样；
- 数据划分、交叉验证 fold；
- 人工评价者差异；
- 硬件、运行时或外部服务波动。

随后记录重复次数、统计单位、中心趋势、离散或区间方法。标准差描述观察值的离散，标准误和置信区间涉及估计不确定性；它们不能只写成统一的 `±`。多个 seed 的波动也不能自动代表换数据、换场景后的泛化不确定性。

主张“有意义地更好”前，预先给出任务上的实际意义门槛、非劣门槛或所需效应；如果做显著性检验，报告假设、检验、配对单位、多重比较处理和效应量。无法进行可靠推断时，报告描述性结果并收缩结论。

## 人工评价与模型评审

人工评价至少固定：

- 评价构念和 rubric，避免只写“质量”“自然”或“有用”；
- 完整说明、示例、边界案例和试标校准；
- 样本来源、数量、分配、顺序随机化和是否盲法；
- 评价者人数、相关背景、招募、报酬、同意和适用的伦理审批；
- 每个样本由谁评价、分歧如何裁决、协议一致性如何报告；
- 无效提交、缺失评价和退出如何处理。

使用模型作为评审者时，还要锁定模型与版本、系统 / 用户 prompt、采样参数、重试和解析规则；用人工标注样本检查偏差、一致性和位置 / 长度等伪线索。模型分数不能因为生成得很像人工评分就自动成为可靠测量。

## 效率与系统指标

报告延迟、吞吐、显存、能耗或成本时，固定：

- 硬件、软件、精度、batch、输入长度与并发；
- 是否包含加载、预处理、网络和后处理；
- warm-up 次数、测量次数、同步方式与缓存状态；
- 均值之外的中位数和尾部百分位；
- 失败、超时、重试与费用计算口径。

不同硬件或云服务结果只能在明确条件下比较，不能把单次最短时间写成稳定延迟。

## 运行前冻结与变更规则

评价协议至少冻结以下文件：

```text
evaluation_spec.md
dataset card 与 split manifest
evaluation script / commit / environment
逐样本预测输出格式
主指标与决策门槛
人工评价说明和 rubric（如适用）
```

协议冻结后发现实现错误，可以修正，但必须新建版本，说明错误影响、旧结果是否作废以及重新运行范围。不能静默更换主指标、删掉失败样本或只报告更有利的 aggregation。

## 参考依据

- [scikit-learn Metrics and scoring](https://scikit-learn.org/stable/modules/model_evaluation.html)：定义分类、回归、聚类和多标签指标，并区分 macro、micro、weighted 等聚合；
- [Google Classification Metrics](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall)：把 accuracy、precision、recall 与类别平衡、阈值和错误代价联系；
- [NeurIPS Paper Checklist](https://neurips.cc/public/guides/PaperChecklist)：要求为主要实验适当报告误差条、区间或统计检验，说明变异来源和计算方式；
- [ACL-IJCNLP Reproducibility Checklist](https://2021.aclweb.org/calls/reproducibility-checklist/)：要求清楚定义评价统计量、运行次数、选择标准和汇总统计；
- [Twenty Years of Confusion in Human Evaluation](https://aclanthology.org/2020.inlg-1.23/)：说明人类评价构念和报告方式不统一会削弱比较与复现；
- [ACL Ethics：Researchers](https://ethics.aclweb.org/roles/researchers/)：要求报告实验变异，并为人工参与者提供完整说明、招募、同意、报酬和伦理信息。

## 完成标准

运行正式实验前，你应能：

- 展示已填写并冻结的[评价协议卡](../templates/14-evaluation-spec.md)；
- 用一个小型手算或已知样例验证评价实现；
- 从保存预测重新计算主指标；
- 解释统计单位、聚合、阈值、不确定性和实际意义门槛；
- 说明测试集何时可见，以及什么决策不能再根据测试结果修改；
- 明确主指标支持的主张和仍需辅助证据回答的问题。
