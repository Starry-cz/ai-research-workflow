# 第一项导师任务：先确认授权边界，再开始执行

这份指南用于第一次接到导师、师兄师姐或项目负责人的科研任务时。目标不是要求每个动作都等待审批，而是把任务说明、技术权限和研究决策权分开：在已确认范围内独立推进，遇到会改变共享状态、研究协议或对外关系的动作时及时确认。

```text
复述任务与交付
  → 识别任务负责人和决定负责人
  → 盘点代码、数据、算力与对外权限
  → 将动作分为直接执行 / 先确认 / 停止升级
  → 只在已授权范围内留下第一条证据
```

> 能看到文件、拥有服务器账号或具备 Git 写权限，只说明技术入口存在，不自动代表当前任务允许读取、修改、上传、删除或发布。

## 1. 哪些情况必须先使用本指南

- 只收到一句“先把这个项目跑一下”“试试这个方法”或“看看能不能改进”；
- 第一次进入实验室仓库、共享服务器、数据目录或云平台；
- 任务涉及未公开代码、受限数据、匿名审稿材料、个人信息或尚未发表的结果；
- 可能改变 baseline、数据划分、评价脚本、共享分支或已有实验产物；
- 需要购买算力、调用付费 API、把材料交给外部 AI / 云服务或联系外部人员；
- 准备公开 Issue、Pull Request、仓库、演示、预印本或投稿材料。

公开教学仓库的本地练习通常可以直接开始，但仍应遵守许可证、使用条款和安全边界。真实项目已有更严格的实验室、机构、资助方或数据政策时，以其规则为准。

## 2. 先写一张“任务授权卡”

不新增独立模板；把以下字段填入[研究简报](../templates/01-research-brief.md)或当前[原子任务卡](../templates/06-daily-task-card.md)：

```text
任务来源与任务负责人：
要回答的问题、交付物、截止与验收人：
允许读取的位置：
允许写入的位置、分支与输出目录：
允许运行的设备、时长、费用或配额：
允许传出的内容与渠道：
必须保持不变的 baseline、数据和评价协议：
需要再次确认的决定及其负责人：
禁止访问、上传、删除或公开的对象：
停止与升级联系人：
确认记录的位置和日期：
```

不知道的字段写“待确认”，不要根据账号权限、历史惯例或 AI 推测补全。任务负责人负责解释交付，决定负责人负责批准研究协议、资源或对外动作；两者可能不是同一个人。

## 3. 用三类动作决定能否继续

### 绿色：`EXECUTE_WITHIN_SCOPE`

在任务、项目规则和访问范围已经明确时，可以独立完成：

- 阅读获准访问的 README、论文、代码、配置和已有记录；
- 查看 `git status`、`git log`、remote、分支和脚本帮助等只读信息；
- 在允许的位置 clone / fork，或新建个人分支、个人输出目录；
- 运行项目已记录的帮助、测试、预训练评测或小规模命令；
- 在已批准的数据、设备、时间和费用内做不改变协议的短试跑；
- 保存自己的任务卡、命令、日志、配置、diff 和失败记录；
- 汇总发现并提出一个有证据、可回答的问题。

绿色动作仍不能越过许可证、数据条款、服务器规则或项目已有流程。发现规则冲突时立即转为红色状态。

### 黄色：`CONFIRM_BEFORE_CHANGE`

以下动作通常可恢复，但会改变研究解释、共享状态、资源或外部关系，应先由对应负责人确认：

- 改研究问题、交付范围、baseline、数据来源、split、预处理、指标、阈值或评价脚本；
- 向共享分支 push、合并 PR、覆盖团队配置、移动目录、升级依赖或修改共同使用的 Notebook；
- 首次使用完整训练、大规模下载、云 GPU、付费 API 或超出约定配额；
- 把项目内容发送给外部 AI、在线 Notebook、网盘、标注平台或其他第三方服务；
- 联系论文作者、开源维护者、数据提供方或会议组织者，并让对方可能把你视为代表课题组；
- 新增或移除协作者、调整仓库可见性、发布代码 / 数据 / 模型 / 结果、提交预印本或演示；
- 删除、覆盖、迁移或缩短共享日志、checkpoint、数据和证据产物的保留期；
- 使用尚未核验许可、伦理审批、同意范围或再分发条件的资产。

确认不应只是“老师知道这个项目”。记录具体动作、范围、成本、风险、批准人、日期和证据位置。若负责人只批准 pilot，不要扩展为完整训练或公开发布。

### 红色：`STOP_AND_ESCALATE`

遇到以下情况不要自行绕过、补救或继续试探权限：

- 需要上传密钥、个人信息、敏感 / 受限数据、未公开稿件或匿名审稿材料；
- 任务与数据使用条款、知情同意、伦理审批、机构政策、法律或平台规则冲突；
- 被要求绕过访问控制、共享他人账号、隐藏运行来源或使用未经授权的数据；
- 被要求编造、篡改、选择性隐藏数据、代码、失败实验、引用、图表或结果；
- 删除或覆盖目标不清、没有恢复路径，或者可能影响他人工作；
- 已发生密钥泄露、数据外传、权限误配、安全事件或错误公开；
- 出现署名、归属、利益冲突、对外承诺或研究责任争议；
- 不同负责人给出互相冲突的指令，且无法判断谁拥有最终决定权。

停止时保留时间、命令、状态和必要证据，但不要继续复制敏感内容。使用项目指定的负责人、数据管理员、伦理 / 安全渠道或机构流程升级；本仓库不能替代这些正式渠道。

## 4. 第一个 30 分钟怎么做

1. 用两三句话复述任务、产物、截止和明确非目标；
2. 只读检查仓库、数据说明、服务器规则、已有任务和最后可信结果；
3. 把下一步动作放入绿色、黄色或红色；
4. 若全为绿色，在个人分支或获准输出目录运行最快的官方命令；
5. 若有黄色项，把相互关联的问题合并成一次确认，并附现状、选项、代价和自己的建议；
6. 若有红色项，暂停相关动作，记录阻塞和升级对象；
7. 将决定与证据写回研究简报或任务卡，不只保留在口头或聊天窗口。

可使用以下确认句式：

```text
我理解本次交付是【产物】，截止为【时间】，本轮不改变【非目标 / 冻结协议】。
我已确认可以在【分支 / 目录 / 设备】读取和运行【对象】，预计使用【预算】。
下一步需要【具体动作】，它会影响【共享状态 / 数据 / 评价 / 对外关系】。
我建议【方案】，回退方式是【方式】；请确认是否按该范围执行。
```

这不是固定话术。重点是让对方能够判断一个具体决定，而不是阅读全部探索过程。

## 5. Git 与共享代码的边界

GitHub 的 `Read / Triage / Write / Maintain / Admin` 是平台权限层级，不是研究任务委托书。即使拥有 `Write`：

- 先按项目约定使用分支、Issue、PR、review 和 CI；
- 保护分支要求的审阅不能用“我已经本地测试过”替代；
- fork 的可见性与上游相关，私有内容不能随意复制到个人公开仓库；
- 允许维护者编辑 fork 分支可能同时影响 workflow 与 secrets，应阅读 GitHub 的安全提示；
- 对上游公开提交 Issue / PR 前，先确认最小复现不含私有材料，并确认是否代表个人还是课题组。

技术权限过大时采用最小权限原则：只使用完成当前任务所需的最低角色、分支和数据范围。

## 6. 数据、算力与外部 AI 的边界

开始前至少明确：谁有访问权、谁授予访问、允许在哪些设备处理、能否复制或再分发、项目结束后如何保留或删除。匿名化不自动消除重识别风险，受限数据也不因论文要求复现而自动变成公开数据。

外部 AI、在线 Notebook、云盘和实验跟踪服务都属于新的处理位置。没有明确允许时，只使用公开材料、合成数据或不含项目内容的最小示例；不要把“服务可登录”当成数据获准上传。算力也应记录配额、付费人、停止阈值和资源释放责任。

## 7. AI 可以帮什么，不能决定什么

AI 可以：

- 从现有文档提取任务、资产、未知项和冲突；
- 把大任务拆成带产物、验收和时间盒的动作；
- 草拟确认问题、比较选项并检查是否遗漏风险；
- 在获准范围内解释代码、生成最小 patch 和核对 diff。

AI 不能：

- 根据文件可见、账号权限或“导师让我做”推断授权；
- 代替数据所有者、项目负责人、伦理审查或机构批准；
- 自动批准改变数据、评价、成本、共享状态或对外发布；
- 用自动运行成功证明论文、引用、实验或结论可信。

自动化研究系统的人工检查点、预算和版本化值得借鉴，但零基础真实项目默认不启用“自动批准”。每次暂停点都要指定谁能批准什么，而不是把所有确认都交给同一个按钮。

## 8. 只选择一个任务状态

| 状态 | 含义与下一步 |
| --- | --- |
| `READY_WITHIN_SCOPE` | 任务、资产、写入位置、预算和非目标明确；只执行已授权动作。 |
| `NEEDS_CONFIRMATION` | 某项研究判断、共享修改、成本或对外动作待负责人确认；其余绿色动作可继续。 |
| `NEEDS_ACCESS` | 缺少必要代码、数据、设备或记录权限；通过正式路径申请，不借用账号或密钥。 |
| `POLICY_ESCALATION` | 涉及伦理、隐私、安全、许可、合同或机构规则；暂停相关动作并使用正式渠道。 |
| `BLOCKED_CONFLICT` | 指令或负责人冲突，无法确定最终决定权；保留证据并升级，不自行选择最方便的解释。 |

`NEEDS_CONFIRMATION` 不等于整项工作停摆。可以继续不依赖该决定的只读检查、公开资料检索、合成数据练习和问题整理，但不能偷偷跨过待确认边界。

## 9. 验收清单

- [ ] 任务负责人、决定负责人、交付、截止和验收方式明确；
- [ ] 允许读取、写入、运行、分享和付费的范围均有来源；
- [ ] baseline、数据与评价协议中必须保持不变的部分已写明；
- [ ] 每个下一步动作已分到绿色、黄色或红色；
- [ ] 共享分支、外部服务、公开沟通和删除动作没有仅凭技术权限执行；
- [ ] 敏感、受限、匿名或未公开材料没有进入未授权位置；
- [ ] 待确认问题包含选项、影响、建议和明确批准人；
- [ ] 当前任务状态、确认日期和证据位置已写回唯一记录。
