# 公平调参与搜索预算

这份指南用于 baseline 已通过稳定化门、准备比较候选方法时。它解决的不是“怎样把分数调到最高”，而是：在有限资源下，如何让 baseline 与候选方法获得可比较的调参机会，并让每一次尝试都能被追溯。

```text
冻结问题与测试权限
  → 区分科学变量和干扰超参数
  → 声明搜索空间、算法与预算
  → 记录全部 trial
  → 只在验证集上选择配置
  → 冻结配置后运行确认性实验
  → 披露搜索成本、失败与变更
```

## 什么时候必须使用

出现以下任一情况时，在运行正式方法比较前使用本指南：

- 候选方法引入新的学习率、损失权重、层数、阈值或训练日程；
- baseline 使用默认参数，而候选方法准备反复调整；
- pilot、短训练或小数据用于筛选配置；
- 使用 grid、random、Bayesian、Optuna、sweep 或人工观察曲线后继续改参数；
- 已经试过多个配置，准备挑一个结果进入论文表格；
- 测试结果已经看过，仍想修改配置后再次报告同一测试集。

如果只是在调试代码能否运行，不需要完整搜索，但必须把运行标记为 `debug`，不得把其结果升级成方法证据。

## 1. 先分清三类变量

| 类型 | 判断与例子 |
| --- | --- |
| **科学变量** | 本轮真正要研究的改变，例如新模块、新损失或新采样策略。它决定研究主张，不应在看完结果后悄悄更换。 |
| **共享干扰超参数** | 会影响所有方法、但不是研究对象的设置，例如基础学习率、batch size、训练步数、weight decay、checkpoint 规则。 |
| **方法特有干扰超参数** | 只有某方法需要，但仍不是研究主张本身的设置，例如新损失权重、模块宽度或路由阈值。 |

“候选方法新增了参数”不等于它可以获得无限次试错；“沿用论文默认值”也不等于 baseline 已被公平调优。先在[实验卡](../templates/04-experiment-card.md)中写出变量分类，再决定搜索方案。

## 2. 冻结三个预算

不要只写“GPU 允许范围内”。至少同时声明：

| 预算 | 必须写清的内容 |
| --- | --- |
| **总搜索预算** | 最大 trial 数、总 GPU / CPU 时、墙钟时间、费用和截止条件。 |
| **各方法预算** | baseline 与每个候选允许的搜索空间、最大 trial 数、单次训练上限、早停或剪枝规则。 |
| **确认预算** | 配置冻结后，每个方法使用的 seed、fold、重复次数、完整训练规模和最终评测次数。 |

公平不一定要求每种方法具有完全相同的参数个数或逐秒相同的成本，而是要求机会可比较、差异有理由且成本被报告。例如不同优化器可以有不同的特有参数空间，但不能让候选运行 100 个 trial、baseline 只用一次未经核验的默认配置，然后把差异全部归因于方法。

资源不足时，优先缩小比较范围、搜索空间或结论强度；不要通过隐藏额外尝试制造“公平”。

## 3. 选择可辩护的比较方案

### 方案 A：锁定共同配置

仅当已有强证据表明共同配置对两种方法都合理，而且候选改动不太可能改变最优训练条件时使用。必须记录证据，并把结论限定为“在该锁定协议下的比较”。

### 方案 B：分别搜索，可比预算

为 baseline 和候选分别建立 study，在各自合理的干扰超参数空间内搜索，再用同一验证指标和选择规则选出配置。这通常是方法比较更稳妥的默认方案。

### 方案 C：先探索，再冻结确认

当预算很小或搜索空间未知时，先用 pilot 识别数量级、不可行区域和训练故障；随后明确结束探索，冻结新搜索空间与确认协议。pilot 的所有尝试仍计入披露，但不能直接与确认性结果混在一起计算均值。

如果三种方案都承担不起，应将结果标记为 `EXPLORATORY_ONLY`，不要写成方法优越性结论。

## 4. 建立完整 trial 台账

每个已启动的尝试都占用搜索机会。成功、失败、被剪枝、手动中断和配置错误都要保留状态。最低字段如下：

```text
study_id / trial_id
方法与科学变量值
完整配置或 config 路径
代码 commit、数据 revision、环境和命令
搜索算法及其版本
父 study、启动时间和触发原因
预算上限与实际资源消耗
验证指标、checkpoint 和选择状态
completed / pruned / failed / invalid / interrupted
失败或排除理由
日志、曲线、checkpoint 和结果路径
```

人工看曲线后调整参数也是搜索，不应记成“经验设置”。如果搜索空间、早停规则或目标指标发生变化，新建 study 版本，并保留上一版结果。

## 5. 只在验证数据上选择

运行前写定：

- 哪个验证指标用于排序，方向是什么；
- checkpoint、阈值和超参数的选择顺序；
- 并列时如何处理；
- NaN、超时、失败 trial 与缺失指标如何处理；
- 搜索结束条件，以及搜索边界何时允许扩展；
- 最终测试集首次可见的条件。

从多个配置中选择最好的一个会利用验证集偶然性。尝试越多，最好验证分数越可能偏乐观。因此最终报告不能只给最佳配置，还要披露搜索规模、搜索空间、失败比例和选择规则；配置冻结后，再用预先声明的 seed 或 fold 运行确认性实验。

看到测试结果后再改学习率、seed、阈值、数据子集、后处理或排除规则，会使测试集参与选择。此时必须新建协议版本，将旧测试结果标记为已暴露；若没有新的独立测试证据，后续结果只能降级为探索性观察。

## 6. 正确使用 pilot、早停与剪枝

- pilot 用于排错、估算资源和排除明显不可行区域，不直接证明完整规模有效；
- 短训练选出的最优参数可能不适用于完整训练，升级规模后必须重新检查；
- 早停和剪枝规则要在各方法间保持可比，并计入已尝试 trial；
- 如果某方法普遍启动慢，按早期分数剪枝可能系统性偏向另一方法，需要调整规则或降低主张；
- 最优点落在搜索边界时，不能直接宣称已经找到该方法的合理配置；应扩展边界，或明确预算限制；
- 大量 trial 发散或失败可能意味着搜索空间不合理，也可能暴露实现错误，不能全部静默删除。

## 7. 从搜索进入确认性实验

进入确认运行前，至少满足：

- baseline 与候选的搜索机会已经审计；
- 搜索空间、算法、trial 上限、失败与剪枝全部可追溯；
- 选择只使用允许的训练 / 验证信息；
- 最终配置已保存，并固定代码 commit 与配置校验值；
- seed、fold、统计单位、主指标和停止门槛已冻结；
- 测试集尚未用于本轮配置选择；
- pilot 与确认性运行有不同的 `study_id` / `run_id`。

然后作一个且仅一个决定：

| 状态 | 含义与下一步 |
| --- | --- |
| `FAIR_TO_COMPARE` | 搜索机会与选择规则可辩护；允许进入确认性比较。 |
| `RE-TUNE_BASELINE` | baseline 的搜索空间或机会明显不足；先补 baseline，不比较方法优劣。 |
| `REDESIGN_SEARCH` | 边界、失败率、剪枝或指标选择有问题；重新设计 study。 |
| `EXPLORATORY_ONLY` | 预算或测试污染无法消除；只报告探索性现象与限制。 |
| `STOP_BUDGET` | 继续搜索不符合资源或时间上限；停止并收缩主张。 |

## 8. 最低披露清单

在报告、论文附录或仓库中至少提供：

- baseline 与候选各自的搜索空间和默认值来源；
- 搜索算法、软件版本、随机状态和自适应 / 人工介入方式；
- 各 study 的计划、完成、剪枝、失败和排除 trial 数；
- 各方法搜索与确认阶段的计算、时间和费用；
- 验证选择指标、checkpoint 与并列规则；
- 最终配置、代码 commit、数据版本和复现命令；
- 所有看过测试结果后的变更及其证据降级；
- 没有被当前预算充分搜索的参数与结论边界。

## AI 与自动调参工具的边界

AI、Optuna 或其他调参系统可以生成候选配置、启动 trial 和汇总曲线，但不能自动决定比较是否公平。研究者必须审核变量分类、预算分配、测试权限、失败排除、配置冻结和最终主张。工具输出的“best trial”只是某个已定义 study 中的选择结果，不自动等于稳定、显著或可泛化的方法优势。

## 依据与延伸阅读

- [Deep Learning Tuning Playbook](https://github.com/google-research/tuning_playbook)：科学 / 干扰超参数、study / trial、公平搜索、预算分配、边界与训练曲线检查；
- [NeurIPS Paper Checklist](https://neurips.cc/public/guides/PaperChecklist)：训练细节、超参数选择、计算资源与不确定性披露；
- [PyTorch Reproducibility](https://docs.pytorch.org/docs/stable/notes/randomness.html)：随机性、确定性与跨环境复现边界；
- [Releasing Research Code](https://github.com/paperswithcode/releasing-research-code)：依赖、训练、评价、权重和精确结果命令；
- [Lightning-Hydra-Template](https://github.com/ashleve/lightning-hydra-template)：配置化实验、独立日志、多 seed 与 sweep 的工程参考；模板本身不证明实验公平。
