# 零基础 AI 科研核心工作流

这份手册承接根目录 README 的“完整科研工作流”。首页用于判断从哪里开始；本页用于真正执行一个项目。不要一次完成所有阶段，只处理当前阶段，并用产物和通过条件决定是否进入下一步。

```text
研究定义 → 文献发现 → 论文与代码映射 → baseline 复现
    → 假设生成 → 实验设计与执行 → 分析与决策 → 写作与归档
                                      └── 优化或转向 ──┘
```

## 使用规则

每个阶段都要留下五类信息：

```text
输入：论文、数据、代码、配置和前序结论
过程：命令、人工判断、修改和失败
输出：文件、指标、图表和候选结论
核验：测试、对照、原始来源和人工检查
决策：继续、优化、转向或停止，以及理由
```

同一时间只推进一个主要问题。没有通过当前门控时，不用“先做创新”掩盖环境、数据、实现或评价协议的问题。

## 四个核心门控

| 门控 | 最低通过条件 |
| --- | --- |
| **G1 方向与 baseline** | 问题边界清楚；资料、数据、训练和评测入口可核验；算力与时间可承受；有备选候选。 |
| **G2 文献与假设** | 关键表述已回到原文；研究缺口具体；假设可以被实验否定。 |
| **G3 复现与实验** | baseline 达到预设容差或差异可解释；数据与评价协议已冻结；主要改动可独立验证。 |
| **G4 证据与交付** | 计划运行、失败和反例已检查；图表可重建；主张不超过证据；提交或发布版本已冻结。 |

## 0. 建立研究台账

先建立项目根目录的 `README.md` 或等价台账，至少记录：

- 当前研究问题、阶段和本周唯一主任务；
- 论文、数据、代码仓库、commit、配置和环境入口；
- 最新 `run_id`、指标、失败项和产物路径；
- 待导师确认的问题、已作决策及理由；
- 下一步动作、完成条件和停止条件。

台账不是日报。只记录会影响复现、解释、协作或决策的事实。

如果项目已经有论文官方代码、实验室目录、tracker 或组会表格，不要先复制本仓库全部模板。按[真实代码库最小接入](ADOPT_WORKFLOW_IN_EXISTING_PROJECT.md)完成只读盘点，为环境、数据、配置、运行和决定指定唯一来源，只补当前阶段缺口。上游文件和现有成熟结构保持不动，直到真实的复用或协作问题触发升级。

**推荐产物**：[研究简报](../templates/01-research-brief.md)、[原子任务卡](../templates/06-daily-task-card.md)。

## 1. 选择方向与 baseline

先选一个能完成闭环的小问题，不以“最新”“最复杂”或“Star 最高”作为第一标准。

### 方向筛选条件

- 能用一句话说明输入、输出、核心困难和评价方式；
- 有两到三篇代表论文，能找到可核验的正式版本；
- 有合法可用的数据、官方或作者代码、训练入口和评测入口；
- 最小评测或训练能在当前设备、预算和时间内完成；
- 即使结果不提升，也能通过失败分析得到可报告结论。

### 首篇 baseline 筛选表

| 检查项 | 通过标准 |
| --- | --- |
| 论文与代码身份 | 论文版本、作者仓库、许可证、commit 和更新状态明确。 |
| 最小运行入口 | 能找到预训练评测、demo、单元测试或小数据命令。 |
| 数据与评测 | 数据来源、版本、划分和官方指标可获得且可合法使用。 |
| 资源预算 | 已估算下载、存储、显存、运行时间和费用。 |
| 可理解性 | 能定位数据加载、模型、loss、训练和评测入口。 |
| 退出与备选 | 写明预检失败后的停止条件，并保留至少一个备选候选。 |

先对两到三个候选做低成本预检，再决定投入对象。不要先下载全部数据或启动完整训练。

**推荐产物**：[首篇 baseline 准入卡](../templates/11-first-baseline-gate.md)。通过后进入 G1。

## 2. 文献发现、筛选与核验

文献检索的目标不是无限增加 PDF，而是形成能支持当前决策的小型论文集合。

1. 从任务、方法、数据集、指标、失败现象和领域术语建立关键词组；
2. 记录数据库、完整查询式、筛选范围、时间和命中数；
3. 按标题、作者、年份、DOI、arXiv ID 和会议版本去重；
4. 先扫描标题与摘要，再对核心论文做定向阅读和精读；
5. 把博客、经验帖和聚合页当作发现入口，关键结论回到论文、官方文档或正式规则；
6. 达到停止条件后转入综合，不用“继续搜索”推迟决策。

第一次检索只使用最小来源组合：一个发现入口用于找候选；DBLP、DOI 或等价来源确认书目身份；出版社 / venue、arXiv 版本或 OpenReview 确认实际原文；准备复现时再核验官方代码、commit、数据和评测。具体执行见[论文发现与原文回溯](PAPER_DISCOVERY_FIRST_PASS.md)。

最低停止条件可以是：核心方法链条已覆盖；新增检索连续两轮主要得到重复路线；当前问题、主要分歧和待验证缺口已经能写清。

**推荐产物**：[文献检索账本与领域地图](../templates/07-literature-search-log.md)。

## 3. 论文阅读与代码映射

先决定阅读深度，不对所有论文使用同一种精读方法：

- **扫描**：判断是否相关，只看标题、摘要、图表、结论和元数据；
- **定向阅读**：为当前问题查方法、数据、实验设置、结果或局限；
- **精读**：只用于核心 baseline、直接竞争方法和决定实验设计的论文。

核心论文至少完成三轮：

1. **全局地图**：问题、核心主张、主要图表、数据和评价；
2. **方法重建**：输入输出、符号、shape、损失、算法步骤和复杂度；
3. **证据审查**：对照、消融、统计单位、失败案例、局限和结论边界。

随后建立映射：

```text
论文模块 → 公式 / 伪代码 → 仓库文件与类 → 输入输出 shape
         → 配置项 → 日志字段 → 论文表格或图
```

**推荐产物**：[论文阅读卡](../templates/02-paper-reading-card.md)；公式真正阻塞任务时再启用[数学概念卡](../templates/12-math-concept-card.md)。

## 4. 代码复现

复现按风险从低到高推进，不把“程序成功退出”直接称为复现成功。

| 关卡 | 动作与通过条件 |
| --- | --- |
| **C0 身份与资源** | 固定论文版本、官方仓库、commit、许可证、硬件与预算；确认训练和评测入口。 |
| **C1 环境** | 在独立环境运行官方帮助命令、测试、demo 或预训练评测，并保存命令和日志。 |
| **C2 数据** | 核验来源、使用权、revision、样本单位、划分、重复、泄漏和预处理版本。 |
| **C3 结构与 shape** | 跑通数据加载和前向传播，记录关键张量、单位与取值范围。 |
| **C4 梯度与小样本** | 检查 loss、梯度、参数更新，并在极小样本上验证模型可以过拟合。 |
| **C5 完整复现** | 使用预先固定的配置和评测脚本运行；报告全部计划运行、差异和失败。 |

迁移到服务器或云端前，先在本地验证最小命令，并固定代码 commit、环境、数据清单、缓存路径、断点恢复、预算上限和结果导出方式。

复现结论只能是以下之一：达到预设容差；未达到但差异可定位；由于明确限制无法完成。不要用“看起来差不多”或最好一次结果替代判定规则。

进入方法改进前还要通过[baseline 稳定化门](BASELINE_STABILIZATION_GATE.md)：分开记录论文目标值、本地锁定 baseline 和候选方法，并选择 `READY_FOR_CHANGE / REPRODUCTION_ONLY / COMPARATOR_ONLY / REPLACE_BASELINE`。只有 `READY_FOR_CHANGE` 可以作为首次改进的主 baseline；“差异已解释”必须有证据、残余边界，并确认不会与候选改动混杂。

复现阶段不得不修环境或 baseline 时，以及进入第一次方法改动前，都执行[安全改码准入](SAFE_FIRST_CODE_CHANGE.md)：先冻结 base commit 与最近一次可运行证据，把环境修复、baseline 修复、重构、观测和研究改动分开，按风险选择最低检查并逐文件审查 diff。只有取得 `READY_FOR_CHANGE` 且改动状态为 `SAFE_FOR_PILOT`，才进入方法试运行；发现 baseline 或评测变化时返回稳定化阶段。

**推荐产物**：[复现规划](../templates/03-reproduction-plan.md)、[baseline 准入卡](../templates/11-first-baseline-gate.md)、[数据集审计指南](DATASET_FIRST_AUDIT.md)、[数据集卡](../templates/13-dataset-card.md)。

## 5. 从复现走向研究问题

先从观察到的失败和限制出发，再提出方法改动：

```text
现象 → 证据位置 → 可能机制 → 可证伪假设
    → 最小改动 → 预期结果 → 失败时的解释与下一步
```

一个可执行问题应明确：在哪类输入或条件下；哪个 baseline 出现什么可重复现象；为什么现有机制可能导致它；什么实验结果会支持或否定解释。

优先从错误切片、训练曲线、资源瓶颈、消融缺口、跨数据失效和论文明确局限中找问题。避免只写“加入某模块可能提升性能”。

极小数据或短训练的收益只能作为 pilot 信号。进入正式比较前，要在更接近目标协议的代表性规模上检查效应是保持、减弱还是反转；模块来自新论文、顶会或高 Star 项目都不能替代机制假设和新颖性核验。

通过 G2 前，导师、同伴或自己应能指出假设的反例、主要混杂因素和最小验证实验。

## 6. 实验设计与管理

正式比较前先冻结评价协议，包括：

- 主指标及其实现、方向、聚合方式和统计单位；
- 数据版本、split、阈值选择和测试集访问规则；
- baseline、唯一主要改动、固定变量和允许调整的变量；
- 随机种子或重复策略、不确定性表达和决策门槛；
- 资源预算、最大运行数、停止条件和失败处理；
- 人工评价或模型评审的 rubric、校准和审计方式。

如果 baseline 与候选需要选择学习率、损失权重、训练日程、阈值或其他设置，还要先执行[公平调参与搜索预算](FAIR_TUNING_BUDGET.md)：区分科学变量与干扰超参数，分别声明 baseline 和候选的搜索空间、trial 上限、计算预算、剪枝规则和选择指标。公平不要求参数空间完全相同，但不允许“候选反复调参、baseline 只跑默认值”。pilot、失败、剪枝和人工看曲线后的调整都属于搜索尝试。

所有配置只能使用预先允许的训练 / 验证信息选择。最终配置冻结后，再按相同确认协议运行 seed 或 fold。看到测试结果后继续改参数会使测试集参与选择；没有新的独立测试证据时，后续结果必须降级为探索性观察。

最小实验矩阵通常先包含：baseline、候选方法、去掉关键改动的消融，以及一项最相关的稳健性或效率检查。任务和主张不需要时，不为“表格完整”机械增加实验。

每次运行必须关联唯一 `run_id`，并保存代码 commit、配置、命令、环境、数据版本、日志、指标和状态。调试运行用于发现错误；只有符合冻结协议的确认性运行才能支持主要结论。

当关键运行将进入组会决定、论文图表、服务器迁移或由别人接续时，启用[运行交接与冷启动复查](RUN_HANDOFF_REPLAY.md)。先声明接收者需要达到查找、指标核验、最小复跑还是完整接管，再让对方从唯一入口在空目录或另一台机器验证；tracker 页面或作者口头说明不能替代这次检查。

运行后只作四种决定：

- **PROCEED**：证据达到预设门槛，进入下一问题；
- **REFINE**：机制仍合理，进行一次有理由的受控调整；
- **PIVOT**：关键假设被反证，改变假设或路线并新建记录；
- **STOP**：资源、风险或证据表明不应继续。

自动化工具可以执行命令和整理产物，但数据、评价、主要假设、异常结果和对外结论必须人工审核。

**推荐产物**：[第一次安全修改论文代码](SAFE_FIRST_CODE_CHANGE.md)、[评价协议指南](EVALUATION_FIRST_SPEC.md)、[公平调参与搜索预算](FAIR_TUNING_BUDGET.md)、[评价协议卡](../templates/14-evaluation-spec.md)、[实验卡](../templates/04-experiment-card.md)；发生交接事件时再使用[运行交接卡](../templates/16-run-handoff.md)。通过后进入 G3。

## 7. 结果分析与论文表达

先完成结果审计，再开始写结论：

1. 汇总全部预先计划的运行，不隐藏失败或只选最好结果；
2. 区分原始观察、可能解释和最终主张；
3. 比较 baseline 与候选方法的配对错误：共同正确、共同错误、修复样本和破坏样本；
4. 检查替代解释、异常值、数据切片、资源代价和不支持假设的证据；
5. 区分预先声明的分析、探索性发现和后续确认性实验；
6. 为每张图保留输入文件、生成脚本、配置、commit 和输出路径；
7. 为每项主张标注证据位置、适用范围、限制和状态。

推荐写作顺序：方法与实验 → 结果分析 → 相关工作 → 引言 → 摘要 → 结论。写作顺序不改变证据优先级。

**推荐产物**：[从结果到主张指南](RESULT_TO_CLAIM.md)、[结果—主张审计卡](../templates/15-result-claim-audit.md)。

## 8. 投稿、复盘与开源

投稿前从 venue 官方页面核验模板、匿名、页数、补充材料、伦理、数据与代码政策、AI 使用规则和时区。经验帖只能帮助发现问题，不能代替当届正式规则。

提交时冻结真正送审的文件、PDF 校验值、代码 commit、数据和环境版本。评审意见按原子问题拆分为“问题—行动—证据—回复—状态”，只有规则允许时才补实验或修改稿件。

无论接收、拒稿还是停止，都归档：

- 实际提交版本、评审原文、回复和决定；
- 成功、失败和未完成实验；
- 关键决策、已知限制和可继续的问题；
- 可公开代码、配置、环境、权重和复现命令；
- 因隐私、许可证或匿名要求不能公开的内容及原因。

**推荐产物**：[投稿、评审与版本归档卡](../templates/09-submission-review-archive.md)。通过 G4 后再对外发布结论和产物。

## 一次项目的最短闭环

如果上面的流程仍显得很长，先只完成：

```text
一个研究简报
  → 一个通过低成本预检的 baseline
  → 一张核心论文阅读卡
  → 一份可审计复现记录
  → 一个预先写明的单变量实验
  → 一份不超过证据范围的结果报告
```

第一次闭环的目标是形成可靠习惯，不是完成一篇顶会论文。
