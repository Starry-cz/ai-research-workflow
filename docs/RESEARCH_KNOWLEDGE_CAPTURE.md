# 从实验记录到可检索研究知识

这份指南用于把已经停止、解决或转向的实验，转成未来能够检索、核验和谨慎复用的项目知识。它不要求重新抄写配置、指标和日志，也不主张先部署一套复杂知识管理软件。

```text
原始运行 / 文献 / Issue / 会议记录
  → 提炼一条可检索经验
  → 链回唯一证据来源
  → 复用前检查适用范围
  → 回写复用结果或创建替代条目
```

> 原始记录回答“当时发生了什么”，知识条目回答“以后什么情况下值得找到它”。摘要不能替代证据，标签不能替代判断。

## 1. 先判断是否值得提炼

不要为每次 debug 建一张知识卡。满足以下至少一项时再提炼：

- 同一症状已经第二次出现，或很可能在其他配置、机器和成员处重现；
- 失败排除了一个看似合理、以后可能再次被提出的解释；
- 论文目标、本地 baseline 和实际复现之间存在稳定且有边界的差异；
- 一项停止、转向或协议决定需要让未来成员理解“为什么”；
- 一条诊断顺序、保护规则或最小操作已经被真实证据验证；
- 项目准备暂停、交接、投稿、结题或迁移平台，隐性经验可能随人员流动丢失。

一次性的拼写错误、能够直接由代码和测试说明的实现细节、尚未核验的猜测，以及只对当前终端会话有用的临时路径，留在原实验或调试记录即可。

## 2. 六类知识条目

| 类型 | 主要问题 | 典型内容 |
| --- | --- | --- |
| `FAILURE_PATTERN` | 看到某种症状时先检查什么？ | 错误签名、触发条件、已验证原因、排除顺序。 |
| `REPRODUCTION_DELTA` | 为什么本地结果与论文 / 上游不同？ | 身份、协议差异、残余混杂和允许比较范围。 |
| `NEGATIVE_FINDING` | 哪项冻结预测在什么范围内未获支持？ | 有效协议、负结果、替代解释和重开条件。 |
| `DECISION_RATIONALE` | 为什么采用、放弃或转向某条路线？ | 上下文、选项、证据、代价和后果。 |
| `PROTOCOL_GUARDRAIL` | 哪条规则用于防止证据损坏？ | 防覆盖、数据只读、测试集访问、权限和清理门。 |
| `REUSABLE_PROCEDURE` | 哪个步骤已在明确范围内验证？ | 前置条件、最小步骤、完成信号和失败出口。 |

同一条目只回答一个可检索问题。不要把“项目所有经验”写进一页，也不要把未经独立检查的单次观察升级成通用 SOP。

## 3. 最小知识条目

可以把下方字段加入现有 Wiki、Issue、tracker、实验总结或 `knowledge/entries/`。每类事实仍只保留一个主要来源。

```markdown
# KNOW-YYYY-NNN：可搜索的具体标题

- 类型：FAILURE_PATTERN / REPRODUCTION_DELTA / NEGATIVE_FINDING /
  DECISION_RATIONALE / PROTOCOL_GUARDRAIL / REUSABLE_PROCEDURE
- 状态：PROVISIONAL / ACTIVE_LOCAL / CONFIRMED_REUSE / SUPERSEDED / RETIRED
- 负责人、创建日、最后核验日：
- 验证等级与共享等级：V0–V4；S0–S3
- 检索标签：阶段、组件、症状、任务 / 数据 / 模型 / 环境、错误关键字
- 来源：experiment_id / run_id / commit / Issue / 文献 / 决定记录的稳定链接

## 可复用结论
在什么精确范围内，已经知道什么？

## 适用与不适用
哪些身份、前提和症状必须匹配？哪些情况必须重新诊断？

## 已验证诊断或动作
按什么顺序检查？每一步的完成或退出信号是什么？

## 证据与反例
原始证据在哪里？哪些解释已排除？还存在哪些反例和未知？

## 决定、后果与重开
它改变了什么决定？何种新证据会使该条目失效、重开或被替代？
```

### 不要复制原始事实

知识条目应链接而不是复制：

- 配置值回到实际 config；
- 指标回到冻结结果或 tracker；
- 命令与 traceback 回到运行 / 调试记录；
- 数据身份回到 manifest 或数据卡；
- 论文表述回到原文版本和位置；
- 团队决定回到有负责人和日期的原记录。

条目只保存检索入口、限定结论、适用范围、诊断顺序和决定后果。这样原结果更新时，不会留下第二份过期数字。

## 4. 状态与证据边界

| 状态 | 使用规则 |
| --- | --- |
| `PROVISIONAL` | 来自一次可追踪观察或待复核总结；只能作为检索线索，不能直接改变正式协议。 |
| `ACTIVE_LOCAL` | 已由负责人核对来源、边界和安全动作，可用于当前项目内的限定诊断或决定。 |
| `CONFIRMED_REUSE` | 在另一次身份匹配的运行、机器或成员复查中再次有效；仍不表示跨领域普遍成立。 |
| `SUPERSEDED` | 新证据或条件变化使旧条目被新条目替代；保留历史并链接替代项。 |
| `RETIRED` | 已无适用对象或继续保留会误导；保留最小墓碑、原因和日期。 |

状态与 V0–V4、S0–S3 分开：`CONFIRMED_REUSE` 只描述复用历史，不批准论文主张或公开共享；高证据的知识也可能因私有代码、数据或匿名要求保持 S0 / S1。

已被团队采用的条目不要静默改写含义。新证据改变原因、范围或动作时，新建条目并把旧项标为 `SUPERSEDED`；仅修复错别字或失效链接可以在 Git 历史中更正。

## 5. 让知识真正能被找到

### 标题写症状和边界

不写“训练经验”“踩坑记录”“实验问题”。推荐：

```text
非空输出目录触发 FileExistsError 是防覆盖设计
CUDA 版本一致仍可能因编译架构不匹配而加载失败
当前数据版本下论文 split 无法从公开文件重建
```

标题应包含未来检索者会使用的症状、组件或决定对象。

### 使用小而稳定的标签

最低标签组合：

- `stage`：environment / data / baseline / training / evaluation / analysis / sharing；
- `component`：脚本、模块、框架或数据处理环节；
- `symptom`：异常类型、日志关键字、指标模式或观察；
- `scope`：任务、数据、模型、平台与版本；
- `knowledge_type` 和 `status`；
- `access`：对应 S0–S3，不把受限内容放进公开索引。

自由标签过多会产生同义词漂移。项目开始只维护上述字段；确有检索失败后再增加受控词表。

### 维护两列薄索引

当条目达到三条、第二位成员需要检索，或项目准备暂停 / 交接时，建立索引：

| 条目 | 检索与状态 |
| --- | --- |
| `KNOW-YYYY-NNN` + 标题链接 | 类型、stage、component、symptom、scope、状态、最后核验日、替代项。 |

索引不复制结论和数字。受限条目可以公开一个不泄密的存在性元数据，也可以只保留在获授权的私有索引；是否允许暴露标题和标签由数据、合同、匿名和安全规则决定。

## 6. 复用前五项检查

第一次进行检索和复用时，先完成[知识检索与安全复用演练](FIRST_KNOWLEDGE_REUSE_DRILL.md)。演练要求保留自己的原始查询、比较多个候选并排除明确标记的过期 / 近似建议；本节列表是执行参考，不能替代首次实践。

找到条目后不能直接照做，依次检查：

1. **身份**：代码 commit、数据版本、模型、框架、平台和错误签名是否一致？
2. **范围**：条目的“适用 / 不适用”是否覆盖当前问题？
3. **证据**：来源仍可访问，V 等级和反例是否足以支持本次动作？
4. **时效**：最后核验后，上游接口、协议、数据或权限是否变化？
5. **授权**：当前成员是否被允许读取、运行、修改或共享对应资产？

然后只作一种复用决定：

| 决定 | 下一步 |
| --- | --- |
| `APPLY_WITHIN_SCOPE` | 身份和边界匹配；执行最小动作并回写结果。 |
| `VERIFY_BEFORE_APPLY` | 看似相关但存在版本、平台或证据差异；先做低成本验证。 |
| `DO_NOT_APPLY` | 症状相似但原因、权限或范围不匹配；回到当前问题诊断。 |
| `SUPERSEDE_ENTRY` | 新证据改变旧结论或动作；创建替代条目并链接。 |
| `ESCALATE_RESTRICTED` | 需要未授权资产或可能泄露敏感信息；停止并交给负责人。 |

## 7. 回写复用结果

每次复用至少追加一条紧凑记录。避免使用六列宽表，防止 GitHub 窄窗口和手机端把字段拆成逐字换行：

```markdown
### YYYY-MM-DD / REUSE-ID

- 当前身份与症状：
- 决定与动作：
- 结果：
- 对条目状态的影响：保持 / 升级 / supersede / retire
- 证据位置：
```

一次成功复用只能说明它在新的明确范围内再次有效。失败复用同样重要：它可能揭示范围过宽、版本变化或错误原因不同。不要删除失败回写，也不要为了让条目“看起来正确”修改旧证据。

## 8. 渐进式工具选择

```text
1–2 条经验：原实验卡 / Issue 中增加“可复用经验”字段
3 条以上或第二位成员需要检索：Markdown / Wiki 薄索引
运行数量难以手工比较：使用现有 tracker 的 tags、notes 和搜索
数据、实验和团队规模继续增长：评估 DVC、MLflow、ELN 或机构系统
```

选择工具时核对：搜索、导出格式、API、权限、备份、离线访问、学习成本、机构支持和退出策略。不要让笔记系统成为另一项长期工程，也不要把受限实验上传给未经批准的云端 AI。

MLflow / DVC 适合定位 run、参数、指标和版本，不自动生成可信的科学解释；Obsidian、Wiki 或 ELN 适合上下文和检索，不自动保证原始记录完整。两类系统通过稳定 ID 相连，而不是互相复制所有字段。

## 9. AI 辅助边界

AI 可以：

- 从已提供记录中提出标题、标签和候选条目；
- 检查条目是否缺来源、边界、反例、状态或重开条件；
- 按症状、组件和 stage 查找相关条目；
- 比较新旧条目并提出 supersede 草案。

AI 不能：

- 把未运行、未记录或无法访问的内容补成事实；
- 仅凭相似错误消息判定根因相同；
- 用摘要覆盖原始日志、配置、数据或决定；
- 自动把 `PROVISIONAL` 升为团队规则；
- 将私有代码、受限数据、匿名材料或个人信息发送到未授权服务；
- 自动合并互相矛盾的条目并删除历史。

## 10. 经验、项目与规范依据

- [实验失败后，别只写“没做出来”](https://www.xiaohongshu.com/explore/6a3cb42f0000000021020e7b)指出只记录失败标签，之后无法知道失败位置、预期差异、对照、变更条件和下一步排查；本指南将这些问题连接到原证据和检索字段，不把湿实验例子直接当作 AI 实验协议；
- [关于用 Obsidian 做实验记录的感受](https://www.xiaohongshu.com/explore/69e1ac9d0000000023013230)记录了前期搭建成本、碎片整理、本地记录和 AI 总结体验，评论也反映表格录入与工具选择摩擦；本指南吸收“本地可检索与渐进搭建”，不推荐指定插件，也不让 AI 摘要替代原始记录；
- [研究生的实验记录该怎么记，以结果为导向](https://www.xiaohongshu.com/explore/696fa4fb000000001a02bc8e)反映按日期堆过程难以复盘；本指南按未来检索问题组织知识，但不隐藏失败过程；
- [知乎：实验记录需要注意的关键点](https://zhuanlan.zhihu.com/p/534204566)举例说明未及时记录临时改变会让成功条件长期无法重建；其内容偏生物 / 合规实验，本指南只迁移即时身份、变更与原因记录；
- [知乎：如何科学地进行实验设计和记录](https://zhuanlan.zhihu.com/p/69353695)强调实验无论是否符合预期，都应整理其说明的问题和下一步；文中具体笔记软件建议较早且属个人经验，不作为工具选择规则；
- [知乎：上了电子实验记录本，之前的实验记录怎么办](https://zhuanlan.zhihu.com/p/2058238080742594121)反映历史记录迁移、原始数据和 AI 完整性检查需求；该文来自商业 ELN 服务商，只用于确认迁移痛点，不采用产品结论；
- [Architecture Decision Record](https://github.com/architecture-decision-record/architecture-decision-record)用上下文、决定、后果、状态和 supersede 保存软件决策；本指南借鉴不可静默改写和替代链，但研究结论仍需实验与领域方法证据；
- [eLabFTW](https://github.com/elabftw/elabftw)展示可搜索实验、团队权限、导入导出和本地部署的 ELN 机制；它面向实验室服务器和更广泛科研对象，不是零基础 AI 项目的必装依赖；
- [DVC](https://github.com/treeverse/dvc)把参数、指标和 artifact 元数据与 Git 版本关联，支持比较和恢复实验；本指南吸收身份与版本链，首次小实验不要求引入 DVC；
- [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/tracking-api/)支持 tags、notes、Git commit 和可搜索 run；这些元数据用于定位，不会自动证明根因、主张或适用范围；
- [The Turing Way：Electronic Lab Notebooks](https://book.the-turing-way.org/reproducible-research/rdm/rdm-elns/)总结 ELN 的搜索、共享、备份、导出、锁定、安全与学习成本；本指南据此要求退出策略，而非把数字化等同于可复现；
- [FAIR Guiding Principles](https://www.gofair.foundation/fair-principles)强调可查找、带标识和丰富元数据、合格引用、来源与访问条件，并允许数据不可用时继续保留元数据；本指南只作入门级迁移，不声称一张 Markdown 索引即达到正式 FAIR 合规。

经验帖用于发现记录与工具摩擦；GitHub 项目用于比较实现机制；正式规范、团队政策、任务授权和数据权利决定最终记录与共享方式。

## 11. 完成标准

一次知识提炼完成时，应能回答：

- 未来会用什么症状、组件和 stage 找到它？
- 它属于哪一类，当前状态是什么？
- 原始证据、决定和版本在哪里，而不是被复制到哪里？
- 哪些范围可以复用，哪些相似情况不得套用？
- 复用前要核对哪些身份、证据、时效和权限？
- 复用后如何回写，何时 supersede、retire 或升级状态？

第一次提炼时，查看[教学知识索引](../examples/first-workflow-drill/knowledge-index.md)和[已填写知识条目](../examples/first-workflow-drill/knowledge-entry.md)；第一次复用时，完成[知识检索练习](../examples/first-workflow-drill/knowledge-retrieval-drill.md)，不要直接跳到答案。
