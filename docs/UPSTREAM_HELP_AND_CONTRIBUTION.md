# 第一次向开源上游求助与贡献

这份指南用于论文代码、机器学习框架、数据工具或模型仓库出现问题后，判断应该本地排查、向社区提问、提交上游 Issue、先讨论功能、发起 Pull Request，还是改走私密安全渠道。

```text
确认上游与支持范围
  → 在未修改的受支持版本上复现
  → 缩成公开、最小、可执行样例
  → 判断问题所有者与正确渠道
  → Issue / Discussion / 私密报告 / PR
  → 跟踪结论并回写本地研究记录
```

> Issue 是项目的工作项，不是通用答疑窗口；Pull Request 是待审提案，不是自动接受的成果。先让证据和渠道匹配，能够同时节省学习者与维护者的时间。

## 1. 先读取上游的协作约定

在发帖或改代码前，依次检查：

1. `README`、安装文档、FAQ、故障排查和支持版本；
2. `CONTRIBUTING.md`、开发环境、测试命令、代码风格、CLA / DCO 要求；
3. `SECURITY.md` 或 GitHub Security 页面的私密报告入口；
4. Issue / Discussion / Forum / Slack / 商业支持分别处理什么；
5. Issue 与 Pull Request 模板、标签、语言和标题要求；
6. 已有开放与关闭 Issue、版本说明和近期相关提交。

项目没有开启 Issue，或模板明确把安装问答导向论坛时，不要在无关 PR 下追问。上游指定规则优先于本指南。

## 2. 先判断问题属于谁

| 类型 | 识别方式与首选动作 |
| --- | --- |
| **本地使用 / 环境问题** | 只在自己的路径、私有数据、改动、旧版本或不受支持组合中出现。先使用[调试与求助卡](../templates/10-debug-help-request.md)，向同伴、导师、项目论坛或支持渠道求助。 |
| **可复现的上游缺陷** | 在未修改的受支持版本、官方最小示例和公开输入上仍偏离文档或明确预期。搜索重复项后按模板提交 Issue。 |
| **文档缺陷** | 命令、参数、链接或说明与当前实现不一致，且能指出准确位置和可核验修正。按项目规则提交 Issue 或小型文档 PR。 |
| **功能想法 / 设计变化** | 当前行为与文档一致，只是希望新增能力或改变接口。先到 Discussion、RFC 或 feature Issue 对齐需求，不先写大型 PR。 |
| **论文复现或研究分歧** | 论文结果、本地 baseline、数据处理或评价口径不一致，但未证明软件实现错误。先冻结 commit、数据和协议，与导师、作者或研究社区讨论；不要把“分数不同”直接标成 bug。 |
| **安全漏洞或私密问题** | 涉及可利用漏洞、密钥、个人信息、受限数据、未公开代码或匿名材料。使用 `SECURITY.md`、私密漏洞报告或项目指定联系人，不公开细节。 |
| **托管 API / 账号 / 计费问题** | 错误来自云服务、闭源接口、账号或套餐，而非开源实现。使用服务商支持渠道，不提交到名称相近的开源仓库。 |

“不确定”不是提交 Issue 的理由。先收集能区分这些类型的最小证据，再选择渠道。

## 3. 通过六级证据门

准备上游报告前逐级检查：

1. **身份**：仓库、release / commit、模型或数据 ID、安装来源明确；
2. **支持**：该系统、Python、框架、CUDA / 驱动和硬件组合在项目支持范围内；
3. **原始状态**：回退自己的 patch、配置覆盖和预处理后，官方示例仍能触发；
4. **干净环境**：在新的独立环境中按官方步骤安装，排除未声明全局包；
5. **最小公开输入**：使用公开小样本或合成数据，删除无关模块后重新运行；
6. **可执行证据**：另一人可按精确命令得到相同实际行为，并能比较预期结果。

每一级都要保留实际结果。为了“让问题消失”而盲目升级全部依赖、切换模型、放宽测试或替换指标，会丢失问题身份；只改变一个候选原因并记录前后差异。

如果问题无法脱离私有数据复现，不要公开私有输入。可以报告不含敏感内容的现象和环境，随后在获授权的私密渠道继续；证据不足时状态是 `INSUFFICIENT_EVIDENCE`，不是“上游确定有 bug”。

## 4. 选择正确渠道

### 使用文档、论坛或 Discussion

适合安装问答、使用方法、方案比较、功能构想和尚未证明的行为差异。提问仍应提供版本、命令、已查文档和具体问题，但不必把所有疑问包装成缺陷。

### 提交 Issue

适合可行动的 bug、文档错误或项目明确接受的功能请求。提交前：

- 搜索报错原文、API 名、模型 ID、版本号和关键行为，包括关闭 Issue；
- 使用项目提供的模板，不删除必填项；
- 一条 Issue 只处理一个可独立关闭的问题；
- 使用项目要求的语言；没有要求时，选择维护者和主要社区能够理解的语言；
- 说明你是个人复现者还是经授权代表团队，不暗示未经确认的课题组立场。

### 私密报告安全问题

先查看 `SECURITY.md` 和 Security 页面的 “Report a vulnerability”。GitHub 私密漏洞报告只有在仓库启用后才可使用；如果没有入口，按安全政策联系维护者，或公开询问“首选安全联系渠道”而不披露漏洞细节。

不要在公开 Issue、Gist、PR、演示视频或 AI 对话中发布利用步骤、密钥和受限材料。普通功能 bug 不要滥用安全渠道。

### 发起 Pull Request

修正文档或明确小 bug 时，项目可能允许直接 PR；新增功能、接口变化、大型重构和研究方法变化通常应先讨论。是否需要先开 Issue 由上游规则决定。

## 5. 一个可行动 Issue 的最小结构

```text
标题：组件 / 模型 + 可观察行为 + 关键环境

问题摘要：一句话说明实际行为为何偏离文档或明确预期
上游身份：仓库、release / commit、安装来源、模型 / 数据 revision
支持范围：相关文档位置或支持矩阵
最小复现：公开、自包含代码与精确命令
预期行为：依据文档、测试或 API 合同
实际行为：完整错误、日志或最小输出
环境：系统、Python、关键依赖、硬件与驱动
重复性：总是 / 偶发，以及最小重复次数
回归范围：最后正常版本（实际验证过才填写）
已查项目：文档、相关 Issue、尝试与各自结果
安全检查：没有密钥、私有数据、匿名材料和无关日志
具体请求：希望确认缺陷、支持范围、修复方向或文档修正
```

预期行为必须有依据。“我以为会更准”“论文里数字更高”或“AI 说这里有 bug”都不是软件合同。超长日志先缩到相关片段；如果项目允许外部 Gist，上传前仍要逐行检查公开权利和敏感信息。

## 6. 研究代码的特殊分流

论文、代码和模型权重可能对应不同时间点。报告复现差异时，至少区分：

- 论文正式版本与目标表格 / 图；
- 作者官方仓库还是第三方实现；
- 仓库 commit、配置、权重与数据 revision；
- 官方评测、预训练推理、短训练还是完整协议；
- 本地评价脚本、聚合单位和容差；
- 环境差异、随机波动、缺失资产和未公开细节。

只有定位到实现或文档的可观察偏差，才把问题提升为软件 Issue。无法达到论文结果可能是值得讨论的复现结果，但不自动等于维护者需要修复的代码缺陷。研究结论与优先级仍由作者团队和证据决定。

## 7. 从 Issue 到小范围 PR

开始贡献前确认：

1. 问题仍存在，且没有已经进行中的重复修复；
2. 维护者规则允许你处理，必要时已在 Issue 中确认方案；
3. 使用正确的 base branch，在个人 fork / topic branch 工作；
4. 一个 PR 只解决一个问题，不混入格式化、依赖升级和无关重构；
5. 修改前测试能暴露问题，修改后同一测试通过，并运行项目要求的检查；
6. PR 正文链接 Issue，说明改了什么、没有改什么、证据、风险和回退方式；
7. 新增代码、测试、数据和依赖的许可证、来源与贡献协议符合项目要求；
8. AI 生成内容经过逐行理解和验证，并按项目政策披露，不把 AI 评审当作维护者批准。

工作仍不完整时使用 Draft PR。维护者要求拆分、补测或改变方向时，先确认意见再更新；不要通过不断添加补丁把原 PR 扩成另一个项目。

## 8. 收到回复后如何闭环

- `duplicate`：阅读并链接已有结论，本地记录实际适用版本；
- `cannot reproduce`：补充最小命令和环境，不重复粘贴同一日志；
- `unsupported`：转到受支持组合，或收缩为本地兼容记录；
- `question / use forum`：按维护者路由转移，不争论标签名称；
- `wontfix / out of scope`：记录上游边界，决定本地 patch、替代项目或停止；
- 已修复：在声明修复的版本 / commit 上重新运行最小复现，再关闭本地阻塞；
- 无回复：不要高频催促；在有新证据、项目规定的时间或实际影响变化时再跟进。

上游关闭 Issue 不能证明你的研究问题已经解决；本地仍要把上游结论、验证 commit、运行结果和下一步写回复现记录。

## 9. AI 辅助边界

AI 可以帮助：搜索疑似重复项、缩减样例、整理环境、草拟标题和 Issue / PR 正文、翻译语言、审查敏感信息与 diff。

AI 不能替你确认：问题真实运行过、支持范围、上游所有权、公开许可、漏洞严重性、论文实现错误或维护者已经接受方案。提交人要能运行每条命令、解释每个改动，并对公开内容负责。

## 10. 只选择一个当前状态

| 状态 | 含义与下一步 |
| --- | --- |
| `LOCAL_USAGE_RESOLVED` | 文档、配置、路径或本地环境问题已找到；回写记录，不提交上游。 |
| `ASK_COMMUNITY` | 尚未证明缺陷，属于使用问答；转论坛、Discussion、同伴或导师。 |
| `UPSTREAM_ISSUE_READY` | 未修改的受支持版本可最小复现，Issue 包完整且无敏感内容。 |
| `DISCUSS_BEFORE_CHANGE` | 功能、接口、研究方法或大范围方案需要先与维护者对齐。 |
| `READY_FOR_PR` | 范围已确认，小 diff、测试、来源与贡献要求均通过。 |
| `PRIVATE_REPORT` | 涉及安全、隐私或受限材料；只走获准私密渠道。 |
| `RESEARCH_REVIEW` | 核心是论文结果、数据或评价解释；回到导师、作者与研究证据审查。 |
| `INSUFFICIENT_EVIDENCE` | 尚不能区分本地与上游问题；继续最小化，不发布确定性指控。 |

## 11. 提交前清单

- [ ] 已阅读 README、支持范围、CONTRIBUTING、SECURITY 与模板；
- [ ] 已确认仓库、版本、组件和真正的问题所有者；
- [ ] 已搜索开放 / 关闭 Issue、Discussion、文档和版本说明；
- [ ] 已在未修改的受支持版本与干净环境中重新运行；
- [ ] 最小复现使用公开或合成输入，另一人可以执行；
- [ ] 预期行为有文档、测试或接口依据；
- [ ] 一条报告只包含一个问题和一个明确请求；
- [ ] 没有密钥、个人信息、受限数据、未公开论文和匿名材料；
- [ ] 功能或大型改动已先讨论，PR 范围与测试可审查；
- [ ] 已选择当前状态，并把上游链接和后续验证写回本地记录。

## 依据与延伸阅读

- [GitHub：贡献指南](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)与[Issue / PR 模板](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates)：项目可以规定有用 Issue、PR 和社区行为所需信息；
- [GitHub：创建 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)与[创建 Pull Request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)：重复项提示、分支、base / head、Draft PR 和 Issue 关联；
- [GitHub：私密报告安全漏洞](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately)：私密漏洞报告依赖仓库启用状态；没有入口时应遵循安全政策并避免公开细节；
- [PyTorch](https://github.com/pytorch/pytorch)：将初学者问答、一般交流、bug 和新功能分到不同渠道，并建议新功能先讨论；项目规则会变化，提交时以当前文档为准；
- [Qwen Issue 模板](https://github.com/QwenLM/Qwen3.6/blob/main/.github/ISSUE_TEMPLATE/bug_report.yml)：要求明确模型 / 框架、最小复现、精确命令、预期 / 实际、环境、一个报告一个问题，并把不同产品路由到对应仓库或服务；
- [Transformers Issue #33405](https://github.com/huggingface/transformers/issues/33405)：完整 traceback 仍不足以确定所有者，具体模型与集成边界会影响路由；单个案例只说明问题所有权的重要性；
- [小红书：Python 环境要配死了](https://www.xiaohongshu.com/explore/68a2ff42000000001b01e5b5)与[跑 baseline 常见的坑](https://www.xiaohongshu.com/explore/6925b658000000001d03acfb)：环境、CUDA、路径、预处理和显存问题容易混成“上游代码不行”；个人经验用于识别痛点，具体判断回到官方支持范围，页面可能需要登录；
- [知乎：如何正确地在 GitHub 上提 Issue](https://www.zhihu.com/question/21235917/answer/203370582)：强调遵循模板、说明环境、复现、预期和实际，并考虑项目主要语言；回答年代较早且属个人经验，不替代当前项目规则；
- [知乎：如何加入开源项目](https://www.zhihu.com/question/26640695/answer/2425325922)：从可承担的 Issue、`good first issue` 和带说明的 PR 开始；标签只表示维护者认为适合作为入口，不证明任务仍空闲或一定被合并。
