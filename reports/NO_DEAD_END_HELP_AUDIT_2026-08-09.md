# 检索无命中后的求助与知识回流审计

- 审计日期：2026-08-09
- 审计对象：`Starry-cz/ai-research-workflow`
- 问题编号：I-048
- 结论：原流程能整理最小复现和判断上游渠道，但自助检索无命中或候选无法区分后，没有要求把搜索词、已开候选、负面发现和权限边界无损交给下一位响应者；回复也可能未经本地验证就被当作答案。已补成“检索—交接—回复候选—验证—知识回流”的无死路闭环。

## 1. 当前问题

I-047 已训练读者比较多个候选并安全复用，但主要成功路径仍以“最终能找到适用条目”为前提。若正式索引无命中，现有调试卡虽然有求助字段，却没有单独冻结自助检索结果、下一位问题所有者、一个可区分问题和回复验证状态。新手容易重新发送一句“跑不起来”，使前面的搜索和排除全部作废；接收者给出的路径、命令或判断也可能直接成为第二份未经验证的事实。

## 2. 经验帖对照

- [如何向师兄师姐请教，不让人觉得是伸手党？](https://www.xiaohongshu.com/explore/6a6dccf4000000002c001ef9)建议求助前先查资料和尝试，说明已经做过的努力，选择合适对象，并在得到帮助后反馈结果。它确认了“准备—提问—反馈”摩擦，但属于个人沟通建议，不定义科研证据、保密和上游所有权；
- [希望在读研究生能先思考再求助](https://www.xiaohongshu.com/explore/684991330000000012004857)反映毕业成员持续承担隐性支持、求助者与帮助者责任不清的压力。正文信息较短且是个人感受，本仓库只吸收“先保留自助证据、明确问题所有者”，不把是否求助变成道德评价；
- [如何优雅的应对师弟师妹复现实验](https://www.xiaohongshu.com/explore/6a1e8c5d000000003601d1b3)以讽刺方式呈现复现问题被“慢慢来、加油”敷衍、报错和参数没有被核对的场景。它只能确认模糊答复和身份压制会中断排错，不能作为沟通范例或事实来源；
- [最近带了几个研一新生，谈谈感受](https://www.xiaohongshu.com/explore/674a942c0000000007035d9d)强调按基础、技术和项目决策选择不同求助对象，并提供具体环境、现象和已尝试项；其中个人管理方式和学历比较不作为本仓库的能力判断；
- 知乎文章[作为研究生新手，应该如何和导师沟通](https://zhuanlan.zhihu.com/p/2033116043812532613)建议用问题、证据、可选判断和明确请求沟通。文章由科研服务机构发布，本仓库只吸收结构，不采用固定话术、频率或服务结论；
- 知乎回答[如何正确地在 GitHub 上提 Issue](https://www.zhihu.com/question/21235917/answer/203370582)强调环境、复现、预期与实际。它是较早的个人经验，上游当前支持政策和表单优先。

## 3. GitHub 项目与正式规范对照

- [How-To-Ask-Questions-The-Smart-Way](https://github.com/ryanhanwu/How-To-Ask-Questions-The-Smart-Way)要求提问前搜索、记录尝试、描述症状而非猜测、选择正确渠道，并在解决后补充结果；本仓库吸收查询原文、具体请求和结果回写，但不采用其中对新手带有贬损性的语言，也不把黑客社区礼仪当作师生关系规则；
- [Stack Overflow：Minimal, Reproducible Example](https://stackoverflow.com/help/minimal-reproducible-example)要求样例最小、完整、可复现，并在发出前重新运行；这能提高技术问题的可检查性，但不能判断数据是否可公开、问题归谁所有或研究主张是否成立；
- [KCS：Capture the Requestor's Context](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/030/010/020)要求保留请求者的原始用词、搜索字符串、已查看文章和产品身份，使自助过程不会在转交响应者时成为死路；其 “no dead-ends” 来自服务支持知识管理，本仓库只迁移上下文连续性，不把工单知识直接当作科研证据；
- [GitHub form schema](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema)允许用输入、文本区、下拉和必填验证收集结构化信息；表单完整只能证明字段已填写，不能证明报告属于该仓库、复现真实或回复正确。

## 4. 适用边界

无死路不等于无限升级、必须得到答复或向所有渠道重复发帖。每次转交只选择一个当前所有者和一个能区分下一步的问题；涉及密钥、个人信息、受限数据、未公开代码、匿名审稿和安全漏洞时，保留允许共享的摘要并走获准私密渠道。导师、同伴或维护者的回复一律先标记为候选；只有在当前身份、权限和最小运行中核验后，才能关闭本地阻塞。一次路径拼写错误通常不值得新建正式知识条目。

- 在知识复用教程中加入 `MATCHED / NO_MATCH / AMBIGUOUS / RESTRICTED` 分流、无死路交接包、回复候选验证和知识回流门；
- 升级调试求助卡、上游路由、核心工作流、真实项目接入、README、教学演练和 CI；
- 本例最终状态为 `SELF_RESOLVED_NO_ARTICLE + IMPROVE_FINDABILITY`，只补充现有常见失败入口，不为一次直接使用错误制造新的正式知识卡。

## 6. 验证与剩余风险

自动检查可以证明教学文字、当前 CLI、正式索引和两条运行路径一致；它不能证明真实同伴会回复、回复具备专业性、不同团队接受同一字段，或陌生新手能够无提示完成。下一步仍需使用未参与编写的读者执行预定义任务，记录首次求助点、信息遗漏、错误渠道和回复采纳方式。
