# AI 科研工作流工具库：零基础入门版

面向第一次接触计算机科研、人工智能、机器学习和深度学习的学生与自学者。

这个仓库不是工具收藏夹，也不承诺“用 AI 自动发论文”。它提供的是一条可以执行、检查和复盘的入门路线，帮助你从“不会检索、不会读论文、不会跑代码”，逐步走到：

```text
选定一个可执行的小方向
  → 读懂一篇代表性论文
  → 跑通官方代码与预训练模型
  → 复现一个可信 baseline
  → 完成一次单变量改进实验
  → 用证据写出研究报告或论文初稿
```

> AI 可以帮助检索、解释、配置环境、阅读代码和检查遗漏，但研究者必须理解并核验论文、代码、数据、实验和结论。

## 这个仓库适合谁

### 主要面向

- 没有科研经历，不知道选题、读论文和做实验分别要做什么；
- Python、Git、Linux 或深度学习基础不扎实；
- 能看懂少量代码，但没有完整跑通过论文仓库；
- 收藏了很多课程和工具，却始终没有形成自己的科研闭环；
- 希望使用 AI 辅助科研，同时避免幻觉引用、虚假实验和过度依赖。

### 本仓库重点解决

| 新手问题 | 本仓库提供的解决方式 |
| --- | --- |
| 不知道从哪里开始 | 能力自测、起步清单和八周路线 |
| 基础很多，不知道学到什么程度 | “够用即可”的最低能力门槛和阶段验收 |
| 论文读完仍不会实现 | 论文—公式—图—代码—张量—实验映射 |
| GitHub 项目跑不起来 | 从环境、预训练模型、单批次到完整训练的复现顺序 |
| 一改代码就失控 | 单变量改动、实验卡和回退机制 |
| AI 给出的内容真假难辨 | 来源分层、风险登记和人工验收 |
| 实验做了很多却写不成论文 | 从研究问题到证据表格的一一对应 |

## 第一次使用：从这里开始

不要先下载几十个项目。第一次使用本仓库，只完成下面五件事：

1. 用[零基础准备检查表](templates/00-readiness-checklist.md)判断自己目前在哪一层；
2. 安装 Git、Python 和一种环境管理方式，学会打开终端；
3. 从一个成熟方向中选择一篇有官方代码、训练脚本和可承受算力的论文；
4. 先运行官方预训练模型的评测或演示，不要立刻从头训练；
5. 建立[复现规划](templates/03-reproduction-plan.md)，把缺失信息写入风险登记表。

### 第一天的最低产物

```text
research-project/
├── README.md              # 当前目标、运行入口和进度
├── papers/                # 论文 PDF 或链接索引
├── notes/                 # 阅读卡与问题清单
├── src/                   # 代码
├── configs/               # 可版本化配置
├── experiments/           # 实验记录
└── environment/           # 依赖与环境说明
```

第一天不要求提出创新点。只要能够解释“我要复现哪篇论文、为什么选择它、需要哪些数据和算力、下一步运行什么命令”，就已经完成起步。

## 零基础能力地图

### 能力分级

| 等级 | 当前状态 | 下一阶段目标 |
| --- | --- | --- |
| L0 工具零基础 | 不熟悉终端、Git、Python 环境和 Jupyter | 能克隆仓库、创建环境、安装依赖、运行脚本 |
| L1 AI 基础入门 | 能运行 Notebook，但不熟悉训练、验证和指标 | 能修改样例、解释数据划分、训练循环和评价指标 |
| L2 论文复现入门 | 能跑通训练代码，但无法解释论文与实现对应关系 | 能复现 baseline、定位差异并形成复现报告 |
| L3 研究实践入门 | 能复现论文，准备尝试改进 | 能提出可证伪假设、完成对照实验和失败分析 |

本仓库的核心目标是帮助读者从 L0 或 L1 到达 L2，并为进入 L3 提供规范。

### 三阶段成长路径

课程学习与科研实践不应完全割裂。更可执行的成长方式是边学边留下项目产物：

```text
广度打底：认识基础概念和常用工具，重点完成作业与小项目
    ↓
深度复现：围绕一个细分方向，吃透一篇论文及其代码和实验
    ↓
独立项目：提出可检验问题，完成实验、写作、展示与复盘闭环
```

1. **广度打底**：课程不求一次学完，以“能运行、能修改、能解释”为验收标准；
2. **深度复现**：聚焦一篇资料完整的论文，建立论文—代码—数据—实验映射；
3. **独立项目**：从真实失败现象或方法局限出发，用最小实验检验假设，再决定继续、优化或转向。

### 五项核心科研能力

| 核心能力 | 零基础阶段的可验证表现 |
| --- | --- |
| 发现问题 | 能说明问题为什么重要、现有方法在哪里失效，并形成研究简报 |
| 设计方案 | 能提出可证伪假设，提前写出预期现象、对照组和最小实验 |
| 完成实验 | 能复现 baseline，保留配置、日志、失败项和公平对照 |
| 论文表达 | 能让每个主要主张对应到实验、图表、推导或可靠文献 |
| 研究展示 | 能用五分钟讲清问题、方法、证据、局限和下一步，并回答质疑 |

### 开始科研前的最低能力

你不需要先学完整个计算机本科，但至少需要能完成：

- **终端**：进入目录、查看文件、运行命令、阅读报错；
- **Git**：clone、status、diff、commit，知道 commit 是代码版本；
- **Python**：变量、函数、类、列表和字典、异常、模块导入；
- **环境**：创建独立环境、安装依赖、导出环境文件；
- **数据**：理解样本、特征、标签、训练集、验证集和测试集；
- **机器学习**：理解模型、损失、优化器、过拟合、指标和基线；
- **深度学习**：理解张量、shape、前向传播、反向传播和梯度。

### “学到够用”的判断标准

不要用观看时长判断是否学会。每一项基础都要留下可运行产物：

| 基础 | 最低产物 |
| --- | --- |
| 终端与 Git | 克隆一个仓库，完成一次小修改并查看 diff |
| Python | 写一个读取数据、调用函数并保存结果的小脚本 |
| NumPy / Pandas | 读取数据，检查缺失值、分布和数据类型 |
| 机器学习 | 完成一个训练—验证—测试闭环并解释指标 |
| PyTorch | 写出 Dataset、DataLoader、模型、loss 和训练循环 |
| 论文阅读 | 完成一张有证据位置的论文阅读卡 |

## 可调节的八周入门路线

八周只是参考节奏。每周时间少可以延长，但不要跳过阶段产物和验收。

| 阶段与主要任务 | 阶段产物 | 完成标准 |
| --- | --- | --- |
| **第 1 周：工具与环境**<br>终端、Git、Python 环境、Jupyter | 环境文件、运行日志、第一次 commit | 能独立重建环境并运行脚本 |
| **第 2 周：数据与机器学习**<br>Python 数据处理与机器学习基本概念 | 小数据集训练与评价 Notebook | 能解释数据划分、loss 和指标 |
| **第 3 周：深度学习基础**<br>PyTorch、张量、梯度与训练循环 | 一个可过拟合小样本的模型 | 能解释输入输出 shape 和梯度来源 |
| **第 4 周：方向与 baseline**<br>扫描方向并筛选代表论文 | 研究简报、候选论文表、资源预算 | 选出一篇适合复现的 baseline |
| **第 5 周：论文与代码**<br>精读论文并阅读官方代码 | 阅读卡、模块映射、风险登记表 | 能画出数据流并定位代码入口 |
| **第 6 周：复现与评测**<br>预训练评测、单批次测试、完整复现 | 复现日志、配置、指标差异表 | baseline 达到预设容差或差异可解释 |
| **第 7 周：改进与失败分析**<br>失败案例与单变量改进 | 假设卡、实验矩阵、消融结果 | 改动的效果能被独立检验 |
| **第 8 周：分析与表达**<br>结果分析、写作和复盘 | 研究报告、图表、失败项和下一步 | 每个结论都能回到代码、日志或文献 |

如果第 6 周仍未复现成功，不要急着“做创新”。把环境、数据、预处理、评测脚本、随机种子和官方 issue 逐项核对，复现失败本身也是需要记录的研究结果。

## 完整科研工作流

完整科研不是从选题一路单向走到论文，而是一个带检查点的循环：

```text
研究定义 → 文献发现 → 知识综合 → 假设生成
    → 实验设计 → 实验执行 → 分析与决策 → 写作与归档
                                      └── 优化或转向 ──┘
```

### 阶段产物合同

每个阶段开始前先约定产物，结束后再进入下一阶段。最低应留下：

```text
输入：使用了哪些论文、数据、代码、配置和前序结论
过程：运行了什么命令，做了哪些人工判断和修改
输出：生成了哪些文件、指标、图表、结论和失败项
核验：用什么测试、对照或原始来源检查结果
决策：继续、优化、转向或停止，以及对应理由
```

### 四个核心质量门控

| 门控 | 通过条件 |
| --- | --- |
| G1 方向与 baseline | 问题边界清楚，资料完整，数据合法，算力和时间可承受 |
| G2 文献与假设 | 核心文献已回到原文核验，研究空白具体，假设可以被实验否定 |
| G3 实验设计 | 数据划分、对照组、指标、唯一主要变量、预算和停止条件已锁定 |
| G4 证据与输出 | 每个结论都能定位到真实运行记录或可靠文献，失败和边界已披露 |

门控未通过时不要自动进入下一阶段：小范围修正用 `REFINE`，研究假设或方向需要改变时用 `PIVOT`，资源或证据不足时用 `STOP`，通过后才用 `PROCEED`。

### 0. 建立研究台账

开始检索前，用[研究简报](templates/01-research-brief.md)固定：

```text
项目 ID 与本轮 run ID：
研究方向与任务：
目标用户或应用场景：
候选数据集与许可证：
可用 GPU、时间与预算：
预算上限与停止条件：
目标论文或代表性 baseline：
代码仓库与文献库：
本轮预期产物：
主要风险：
本周唯一优先问题：
```

**阶段验收**：你和协作者能在一分钟内找到论文、代码、数据、环境和最新实验记录。

### 1. 选择方向与 baseline

零基础阶段不追求“大而新”，优先选择成熟、边界清晰、资料完整的小任务。

#### 方向筛选条件

- 最近几年持续有公开论文和代码；
- 存在多个可比较的代表方法，而不是只有一篇孤立工作；
- 有公开数据、清晰指标和合法使用方式；
- 可以在现有 GPU、时间和预算内完成最小实验；
- 任务的输入、输出和评价目标能够用一句话说明。

#### 首篇 baseline 筛选表

| 条件 | 建议 |
| --- | --- |
| 论文 | 优先正式论文或稳定版本，研究问题清楚 |
| 代码 | 优先作者或官方组织仓库 |
| 训练 | 必须有训练入口；只有推理代码不适合作为完整复现起点 |
| 评测 | 指标、数据划分和评测脚本明确 |
| 权重 | 有预训练权重更适合先验证环境，但不是唯一条件 |
| 复杂度 | 模块数量适中，能在纸上画出数据流 |
| 算力 | 先估算显存、训练时间、数据体积和费用 |
| 维护 | 阅读 README、issue、release 和最近 commit |

**阶段验收**：说明为什么选它、准备先运行什么、成功标准是什么、失败后先检查什么。

### 2. 文献发现、筛选与核验

采用四层流程：

```text
主题发现：AI arXiv Paper Portal / Google Scholar / Cool Papers
    ↓
结构化筛选：DBLP / CV Paper Portal / Papers with Code
    ↓
引用追踪：参考文献 / 被引文献 / 作者与同组工作
    ↓
原始核验：论文 PDF / 会议官网 / OpenReview / 官方仓库
```

检索时记录：数据库、日期、完整检索式、纳入与排除标准、去重方式、论文版本、代码状态和待核验信息。

零基础阶段先建立小而精的代表性集合，再扩展覆盖度：

1. 一篇准备复现的核心论文；
2. 两到三篇同任务代表方法；
3. 一篇经典或问题定义来源；
4. 一到两篇近期方法用于了解前沿；
5. 一篇与核心结论相反或暴露失败条件的工作。

**阶段验收**：每篇核心论文都能回到原文，且知道它为什么被纳入当前研究。

### 3. 论文阅读与代码映射

使用[论文阅读卡](templates/02-paper-reading-card.md)，分三轮阅读：

#### 第一轮：建立全局地图

- 论文解决什么问题？
- 输入、输出、数据和指标是什么？
- 作者声称的贡献是什么？
- 哪一张图和哪一张表最关键？

#### 第二轮：重建方法

- 每个模块为什么存在？
- 关键公式的输入、输出和 shape 是什么？
- 数据如何从输入流到损失函数？
- 论文描述、框架图和代码是否一致？

#### 第三轮：审查证据

- 哪个实验支持哪个主张？
- 消融是否真正隔离了变量？
- 是否报告方差、失败案例和计算成本？
- 结论在哪些数据、模型或资源条件下成立？

对核心论文建立映射：

```text
问题定义 → 论文段落 → 框架图 → 数学公式
        → 代码文件 → 函数 / 类 → 张量 shape → 实验配置 → 结果表格
```

看不懂时先记录问题，不要在一个公式上无限停留。优先理解它在完整系统中的作用，再补数学细节。

**阶段验收**：不看摘要也能讲清问题、数据流、核心模块、证据和局限。

### 4. 代码复现

使用[复现规划](templates/03-reproduction-plan.md)，按五个关卡推进。

#### 关卡 A：环境与官方结果

```text
锁定论文版本和代码 commit
  → 建立隔离环境
  → 核对数据与许可证
  → 下载官方权重
  → 运行官方评测或演示
```

先用官方权重验证数据、依赖和评测流程。官方权重跑通，只能说明推理链路基本正确，不能说明训练已经复现。

#### 关卡 B：结构与 shape

- 根据论文图和公式写出模块表；
- 用随机张量或极小数据运行 forward；
- 逐层检查输入输出 shape、dtype 和 device；
- 检查论文、代码和配置之间的差异；
- 缺失细节进入风险登记表，不自行脑补为确定事实。

#### 关卡 C：梯度与单批次过拟合

- 关闭不必要的数据增强和正则化；
- 固定随机种子；
- 用极少样本或一个 batch 训练；
- 检查 loss 是否明显下降；
- 检查关键参数是否有梯度、是否出现 NaN/Inf；
- 检查训练与推理模式、归一化、颜色空间和预处理。

单批次都无法拟合时，不要进入完整训练。

#### 关卡 D：完整训练

- 使用作者配置或记录清楚的等价配置；
- 保存命令、配置、日志、checkpoint 和硬件信息；
- 不用测试集选择超参数或 checkpoint；
- 资源允许时运行多个随机种子；
- 记录中断、异常和所有手动修改。

#### 关卡 E：复现判定

| 状态 | 判定 |
| --- | --- |
| 完全复现 | 核心设置一致，主要指标达到预先设定的容差 |
| 部分复现 | 趋势一致，但因数据、版本或资源差异未达到原结果 |
| 未复现 | 结果或趋势不一致，原因尚未确定 |

不要使用固定的“差几个点都算复现”。容差应结合指标尺度、随机波动、论文报告方式和任务惯例预先确定。

**阶段验收**：另一个人能够根据记录重建环境，并复现官方评测或你的最小结果。

### 5. 从复现走向研究问题

不要从“再加一个模块”开始。先找失效机制：

- 哪些输入或场景表现明显变差？
- 哪个默认假设在当前任务中可能不成立？
- 数据、预处理、损失和评测是否引入偏差？
- 现有方法是在解决原因，还是只改善表面指标？
- 是否存在更简单、成本更低的解释或基线？

形成假设卡：

```text
观察到的现象：
现有方法的局限：
可能机制：
提出的改动：
可检验预测：
最小验证实验：
替代解释：
失败条件与成本：
```

开始修改 baseline 前，必须能解释数据流、关键超参数、评价协议和复现差异。一次只引入一个主要改动，立即验证并保留回退点。

**阶段验收**：实验失败后仍能说明假设的哪一部分被否定，而不是只得到“没有涨点”。

### 6. 实验设计与管理

使用[实验卡](templates/04-experiment-card.md)，先写协议再运行：

```text
研究假设 → 数据与划分 → baseline → 对照组 → 指标
        → 唯一主要变量 → 预算 → 停止条件 → 统计方案
```

#### 参数分组

| 类别 | 含义 | 处理方式 |
| --- | --- | --- |
| 科学变量 | 本轮真正研究的变量 | 系统改变并比较 |
| 干扰变量 | 会影响公平比较的变量 | 合理搜索或在组间统一 |
| 固定变量 | 当前不研究但必须锁定的变量 | 完整记录并说明边界 |

#### 实验矩阵

```text
实验 ID | 假设 | 唯一改动 | 数据与划分 | baseline | 配置
        | commit | seed | 硬件 | 指标 | 结果 | 结论 | 状态
```

#### 最低实验检查

- 数据泄漏、标签问题、颜色空间和预处理差异；
- 训练、验证、测试集的用途是否严格分离；
- 训练曲线、梯度、吞吐量、显存和运行时间；
- 强基线、简单基线和公平调参；
- 主实验、消融、超参数敏感性和计算效率；
- 跨数据集、跨场景或不同规模下的泛化；
- 定性结果、失败案例和适用边界；
- 关键数字能否定位到配置、日志、代码和数据版本。

#### 单次运行清单

不要只依赖终端历史或实验平台页面。每次正式运行至少记录：

```text
run_id / parent_run_id：本轮编号与来源实验
question：本轮只回答什么问题
change：相对 baseline 的唯一主要改动
commit / config / data：代码、配置与数据版本
seed / hardware / budget：随机种子、硬件和资源上限
command：可重新执行的完整命令
status：planned / running / completed / failed / stopped
artifacts：日志、checkpoint、指标、图表和失败信息
verification：测试、对照、复核人与复核时间
```

旧实验记录不得被新结果覆盖。修改假设、数据、评价协议或主要代码时，应创建新的 `run_id`，并保留它与前一版本的关系。

#### 运行后的四种决策

- **PROCEED**：证据达到预设标准，进入下一项实验或写作；
- **REFINE**：假设不变，只修正实现、参数或实验设计后重跑；
- **PIVOT**：证据否定核心假设，回到问题或方案设计阶段；
- **STOP**：价值、资源或证据不足，记录原因后结束当前分支。

**阶段验收**：每轮实验只回答一个主要问题，并得到“采用、回退或继续探索”的明确决策。

### 7. 结果分析与论文表达

先组织证据，再组织文字：

```text
主张 → 支持实验 → 对照组 → 数字或图表 → 反例 → 适用边界
```

建立“声明—证据台账”，再把内容写进正文：

```text
claim_id | 准备写出的主张 | 实验或文献证据 | 文件位置
         | 反例与替代解释 | 适用边界 | verified / pending / rejected
```

实验数字只有在能定位到 `run_id`、配置和日志时才能标记为 `verified`；引用只有在原文确实支持当前表述时才能进入定稿。`pending` 内容可以留在工作笔记中，不能伪装成已确认结论。

论文各部分围绕同一条主线：

```text
引言：背景 → 问题 → 现有局限 → 关键洞见 → 方案 → 贡献
相关工作：技术路线 → 代表方法 → 共同局限 → 本文定位
方法：总体框架 → 问题定义 → 数据流 → 模块 → 设计动机
实验：设置 → 主结果 → 消融 → 泛化 → 效率 → 失败案例
结论：回答问题 → 总结证据 → 说明边界
```

推荐写作顺序：方法与实验 → 结果分析 → 相关工作 → 引言 → 摘要 → 结论。

阅读优秀论文时可以学习其结构、问题定义和论证顺序，但不能直接复制文字或伪装来源。任何重要论断都必须有实验、理论推导或可靠文献支持。

**阶段验收**：每项贡献都能在方法和实验中找到对应证据，结论不超过实验范围。

### 8. 投稿、复盘与开源

投稿前进行三层检查：

| 检查层 | 重点 |
| --- | --- |
| 事实检查 | 引用真实，图表与正文一致，所有实验确实运行过 |
| 逻辑检查 | 问题、方法、实验和结论相互对应，不夸大因果和泛化 |
| 规则检查 | 模板、页数、匿名、伦理、数据、代码和补充材料符合最新 CFP |

项目结束后使用[每周与阶段复盘](templates/05-weekly-review.md)整理：最终研究简报、论文阅读卡、环境、数据版本、代码 commit、主实验、失败实验、决策日志和开放问题。

归档时为最终版本建立只读快照，并增加 `lessons.md`：记录本项目中有效的做法、反复出现的错误、适用条件和下次项目应提前检查的事项。经验必须带场景和证据，不能把一次偶然结果直接写成通用规律。

准备发布研究代码时，最低应提供：依赖说明、训练代码、评测代码、可用的预训练权重，以及能够生成主要结果的准确命令。

## AI 在科研中的正确位置

### 适合交给 AI 辅助

- 解释报错、配置环境和整理依赖；
- 把论文模块、公式、shape 和代码入口整理成表格；
- 搜索候选资料并生成待核验清单；
- 生成测试、检查遗漏和比较代码差异；
- 把实验日志整理为结构化记录；
- 检查写作中的逻辑跳跃、未定义符号和证据缺口。

### 必须由研究者负责

- 研究问题是否值得做；
- 文献是否真实且支持对应表述；
- 数据、划分、预处理和评价协议是否正确；
- 代码修改是否改变 baseline 的公平性；
- 实验是否真实运行、结果是否完整披露；
- 结论、署名、伦理和投稿合规。

### 复杂任务的通用任务卡

```text
目标：要完成什么？
输入：允许读取哪些论文、数据、代码和文件？
边界：不能修改什么，不能假设什么？
步骤：如何拆成可以单独验收的子任务？
检查：必须运行哪些测试、对照或核验？
交付：必须留下哪些文件、日志、结果和失败项？
```

执行前让 AI 复述目标和边界；执行后按原始清单逐项标记“完成、部分完成、未完成、待验证”。新对话或独立检查可以用于反驳方案，但不能替代回到原文和实验核验。

零基础阶段建议采用“AI 执行子任务、研究者通过门控”的协作方式。在 G1–G4 质量门控、数据或评价协议变化、实验结果解释和最终对外发布前必须暂停人工审核，不应默认自动批准。

## 推荐组合

### 组合一：完全零基础

```text
Missing Semester 的终端与 Git
  → CS 自学指南或 OSSU 中的 Python 基础
  → ML for Beginners 完成一个小项目
  → 动手学深度学习完成训练循环
  → 本仓库的首篇论文复现流程
```

### 组合二：会 Python，但不会科研

```text
研究简报
  → Google Scholar / DBLP 建立小型论文集合
  → 论文阅读卡
  → 官方预训练评测
  → shape 检查 + 单批次过拟合
  → 完整 baseline + 复现报告
```

### 组合三：已经跑通 baseline

```text
失败案例与默认假设
  → 假设卡
  → 每轮一个主要变量
  → 主实验 + 消融 + 泛化 + 效率 + 失败分析
  → 研究报告或论文初稿
```

### 组合四：算力有限

优先选择小数据、小模型、参数高效方法、训练免费方法、模型压缩、推理效率、迁移、鲁棒性或可解释性问题。无论选择什么方向，都报告 GPU、训练时间、数据规模、参数量、吞吐量、延迟、显存和资源限制对结论的影响。

## 新手常见误区

| 误区 | 更可靠的做法 |
| --- | --- |
| 先收藏几十个课程 | 每次只选一个主资源，并留下可运行产物 |
| 数学没学完就不能科研 | 围绕当前论文按需补数学，再用代码验证 |
| 代码跑起来就是复现成功 | 区分官方评测、单批次测试、完整训练和结果容差 |
| 越新的论文越适合当 baseline | 首个 baseline 更看重代码、训练、评测、算力和可理解性 |
| 看不懂就让 AI 全部解释 | 先形成自己的问题清单，再核对原文、公式和代码 |
| 一次加入多个模块更容易涨点 | 一次一个主要变量，否则无法解释贡献 |
| 只报告最好的一次结果 | 预先确定协议，报告波动、失败和选择规则 |
| 指标提高就代表研究成立 | 检查公平性、计算成本、泛化、反例和替代解释 |
| AI 写得像论文就可以投稿 | 作者必须理解、核验、修改并承担全部责任 |
| 情绪受一次失败影响 | 把反馈当信息，把复现失败和拒稿纳入正常迭代 |
